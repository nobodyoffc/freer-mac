> **▶ Phase 13 (2026-09-05) — The First FCH board: the way in for a FID that owns nothing.** Every action in this app costs a fee, and a freshly-made FID has nothing to pay one with — it cannot carve, cannot register a DOCK, cannot buy a name. Android answered that with a public request board built on a *nobody* identity, and no phase of this plan had ever owned it. It ships now: **`NobodyBoard`** (the published identity and the wire template) and **`FirstFchBoard`** (posting and reading) in FCDomain, `DockService.fetchNewest`, a **First FCH** pane under Society, and the two places a newcomer will actually find it. 17 new tests; **1 382 green in FCDomain**; app builds and the pane is reachable.
>
> **A nobody FID is one whose private key has been published, and that is the mechanism rather than a leak.** The board is `FHG8DW2eHQ5wNAJQnLNKzYUSo2YKt7ffff`, whose key is in `NobodyBoard.swift` in plain hex. Because everyone holds it, everyone can open what is addressed to the board — and because everyone holds it, nobody owns it: it can be neither trusted nor spoken for. A newcomer with an empty wallet can still park a message at a DOCK, and every existing freer can read it. That is the whole trick, and the FID is **not an independent constant**: a test derives it from the published key, because if the two ever disagree every post goes to an address nobody reads.
>
> **A post is sealed, to a key that is public.** That reads like theatre and is not: a DOCK is a third party that decrypts the request to store the payload and hands those exact bytes back, so *everything* on that path is sealed to its recipient. Making the board an exception would mean a rule spelled "sealed unless somebody remembered otherwise". The consequence is the one thing a reader must not get wrong — decoding the wire bytes alone yields an envelope whose `content` is nil, so a client that stopped there would render the board as **empty** rather than as unreadable. `NobodyBoard.openPost` decodes *and* opens, and a test asserts both halves.
>
> **The template is the spam filter.** A post is `FIRST_FCH_REQUEST|fid|note`, and anything that does not parse is not a row — which matters because a public inbox will hold chatter, another protocol's traffic, and people shouting. It is also what makes a row usable: the helper's side turns ticked rows into transaction outputs, so the FID has to be machine-readable rather than typed into a sentence. Two more filters sit behind it: **latest post per asker**, so somebody who asked three times is one row; and **still broke**, checked with a single `base.freerByIds` over the whole page — an asker who now holds coins was already helped, or is farming, and either way is not a request anyone can answer.
>
> **The cursor keys off the server's `createTime`, never the sender's `timestamp`.** The timestamp is written by whoever posted, so one item could be stamped years ahead and step over every reader's watermark at once. `DockService.fetchNewest` exists for this: the sibling `fetch` walks *our* mailbox forwards around an opaque server cursor and deletes what it takes, which is the wrong shape for an inbox nobody empties and that only grows. This one reads newest-first with a server-side range on `createTime`, and deletes nothing — the items are not ours to delete.
>
> **Android's viewer has a bug that this one does not.** There, the cursor is advanced by *displaying* rows and the rows themselves live only in the activity's memory — so opening the board, leaving it and coming back shows an empty board, because the first visit moved the watermark past everything. Here the pane always reads the whole current board, and the stored cursor answers the different question it is actually good for: has anything appeared since this identity last looked. That is what the opt-in login check counts, and it is **off by default** — helping strangers is something a user opts into, not something the app decides.
>
> **One pane serves two opposite people, because today's newcomer is next month's helper.** If the live FID's balance is zero you get a note field and a Post button; if it is not, you get the list of people waiting, an amount, and one transaction that pays as many as you tick — three separate cashes each by default, so a fresh FID can take two or three on-chain actions in parallel instead of waiting for one coin to confirm between them. The payment is composed here and then goes down the **ordinary** `sendAdvancedFromLive` path: same approval gate, same signing, same cache update, sent from the helper's own FID and never from the board. Coin selection is written locally rather than reusing `CoinSelector.select`, which prices a *single* payment and cannot fund thirty outputs.
>
> **Nothing on the board is actionable, and the UI enforces it.** Anyone on earth can write as that FID, so a row is a FID and a sentence of plain text — no links, no markup, no tappable cards, no payment requests. The pane opens on the warning that says so, with the board's own avatar desaturated by `FidAvatarView(isNobody:)`, which is the mark this app already uses for a published key.
>
> **The last problem was discovery: a pane in a sidebar is no use to somebody who does not know it exists.** So Overview grows a card when the live FID is known to hold nothing — and *known* is the load-bearing word, since `refreshLiveFidInfo` leaves `balance` nil for a FID the index has never seen, which is precisely this newcomer. `AppState.liveFidIsBroke` collapses "zero", "no record at all" and "not fetched yet" correctly, so the banner does not flash at a helper with a full wallet on a slow connection. The helper's half surfaces as an attention tile beside the unread counts, and only for an identity that opted in.
>
> **Ignore and Send now write a decision down, and it expires.** The first cut kept both in the view's memory, which meant closing the pane forgot everything and a helper worked through the same faces on every visit — the failure that makes a shared list unusable. They now record a `BoardDismissal` against the asker's FID, so a second post from the same FID inside the window changes nothing. **Seven days, not forever**: a permanent list is the wrong shape twice over, because a public board is an unbounded source of FIDs and because the decision did not mean that — skipping somebody today is not a promise never to help them, and funding somebody is not a claim they can never need coins again. Expiry alone still does not bound the row, so there is also a cap of 500, evicting the soonest-to-expire first; both are applied on **every write**, which is the entire storage policy, because a write is the only thing that grows the row. The filter lives inside `fetch` rather than in the pane, so the login nudge counts exactly the rows the pane shows rather than badging people you funded last week. And because a persisted hide the user cannot see or undo is a trap, the pane keeps a folded "3 funded, 1 skipped" footer with a per-row Restore — a mis-click on Ignore would otherwise cost a week.

> **▶ Phase 12 (2026-09-04) — Terminal, and the key that opens the server.** The main FID already signs transactions, seals messages and opens FUDP sockets; the one door it did not open was a shell on your own box, where you fell back to `~/.ssh/id_ed25519` — a second identity with its own backup story. It does now: **`SshEd25519Key`** + **`SshWire`** in FCCore, **`SshAgentProtocol`** / **`SshAgentServer`** / **`SshServer`** / **`SshServersStore`** / **`SshLaunch`** in FCDomain, and a **Terminal** pane under Tools over SwiftTerm. 63 new tests; **1 357 green in FCDomain, 202 in FCCore**; app builds and the pane is reachable.
>
> **OpenSSH has no secp256k1 key type, so the FID key cannot be the SSH key — it can only seed one.** `sshd` accepts `ssh-ed25519`, `ecdsa-sha2-nistp256/384/521`, `ssh-rsa` and the `sk-*` variants, and that list is not negotiable on a machine you did not build. So the identity is `HKDF-SHA256(mainPrikey, salt: "fc.freer.ssh.ed25519.v1", info: mainFid) → 32 bytes → Curve25519`, which follows the two domain separations already here (`Configure.verificationToken`, the per-main store key) and needs no rejection loop, because ed25519 hashes its seed and takes any 32 bytes where secp256k1 would need a scalar below the order. What that buys, in the order it matters: **nothing to store** — the key is a pure function of the vault, so the same Configure restored on another Mac derives a byte-identical key with nothing exported; **the money key stays out of reach** — HKDF is one-way and the curves are unrelated, so a fully compromised server reveals nothing about the coins, and the public-key sheet says so in as many words; and **it is bound to the FID**, whose cost is real and also in that sheet — re-mint the main identity and every `authorized_keys` line you have installed is dead everywhere.
>
> **The key is never written down, which is what makes the agent necessary rather than tidy.** `ssh` takes a private key from a file or from an agent; a file would outlive the vault lock and be readable by anything running as you, which throws away the reason to derive rather than store. So **`SshAgentServer`** is a real ssh-agent on an AF_UNIX socket that serves exactly one key and implements four messages — `REQUEST_IDENTITIES`, `IDENTITIES_ANSWER`, `SIGN_REQUEST`, `SIGN_RESPONSE` — and answers `SSH_AGENT_FAILURE` to everything else. **The reduction is the security model:** there is no `ADD_IDENTITY`, no `REMOVE`, no `LOCK`, no `EXTENSION`, so there is no code path that mutates what it holds and nothing for a hostile client to mutate. `ssh -i <public key> -o IdentitiesOnly=yes -o IdentityAgent=<socket>` does the rest; `ssh_config(5)` documents the `.pub`-only form, and `IdentityAgent` is the flag that looks redundant next to `SSH_AUTH_SOCK` and is not — anyone running 1Password, Secretive or gpg-agent has `IdentityAgent` in `~/.ssh/config`, and without it their config wins and our agent is never consulted.
>
> **An agent is a signing oracle for as long as it is up, so its lifetime is a session's, not the app's.** Reach the socket and it will sign anything, which is a login to every server carrying the key — true of every ssh-agent ever shipped. Layered against it: a 0700 per-launch directory under `$TMPDIR` (not Application Support, whose path both eats the 104-byte `sun_path` budget and contains a space that `-o IdentityAgent=` would have to quote), a 0600 socket, a `LOCAL_PEERCRED` uid check on every accept — and the one that actually matters, **it starts on Connect and stops when the last session closes**. `lockAll()` kills the sessions and the agent together, because a channel authenticated before the lock would otherwise stay open on a vault the user believes is closed. Three POSIX details are load-bearing rather than tidy and each is commented where it lives: `FD_CLOEXEC` (SwiftTerm forks and execs without closing inherited descriptors, so the `ssh` child would inherit the listening socket), `SO_NOSIGPIPE` (the default disposition takes the whole app down when a client hangs up mid-write), and unlinking a stale socket before `bind`.
>
> **Nothing here is trusted because we wrote it — every layer is checked against OpenSSH itself.** The frozen key vector is confirmed by `ssh-keygen -l -f`, which parses our `authorized_keys` line and prints the same `SHA256:` fingerprint. The agent is driven by the real `ssh-add`: `-l` lists our key, `-L` prints the exact line the pane offers to copy, and `-D` is refused with the key surviving. And **`SshEndToEndTests` spawns a real `sshd` on a bound port and logs in with the real `/usr/bin/ssh`** using the real argument vector, asserting afterwards that the runtime directory holds nothing but `agent.sock` and `id_ed25519.pub` — with a negative control that takes the agent away and requires the same command to fail, so the pass cannot be coming from some other credential. It is opt-in behind `FREER_SSH_E2E=1`, because it binds a port and spawns a daemon.
>
> **Three UI decisions worth writing down.** The pane is **`TerminalPaneView`**, not `TerminalView`, because SwiftTerm exports a public `TerminalView` and the shadowing produces errors that point everywhere except at the name. Sessions and the agent live on **`AppState`, not in the pane's `@State`**, because the detail column is rebuilt when the sidebar selection changes and a session owned by the view would die the moment you glanced at your wallet. And **`WalletPane.terminal` is `needsKey: false`** — counterintuitive for a pane that plainly cannot work without a private key, and correct by the enum's own rule that the predicate is capability rather than identity: the key comes from the *main* FID through `ActiveSession.sshIdentity()`, available whenever the vault is unlocked, so gating on the *live* FID's `canSign` would close your servers when you switched to a watched FID to read a balance. The one case that really does close it — a main FID with no privkey — the pane says out loud in a banner. Not in this cut: `ssh-copy-id`, port forwarding, SFTP and tabs. The first login is by password in the PTY, you paste one line, and the second is keyless.
>
> **▶ Phase 8.8.5 (2026-08-21) — Statement, and the Publish family closes.** The last of the six, and the only one that is not the others with a different noun: **`Statement`**, **`StatementFeip`** (sn 8 ver 1), **`StatementsStore`**, one carve, a new sidebar entry between Text and Image, and **`PublishStatementView`** with its compose and read sheets. 16 new tests, **1 310 green in FCDomain**, app builds, pane reachable.
>
> **Every difference is a subtraction, and they all follow from one decision: the content is on the chain.** There is no `did`, because a statement whose text lived on a DISK would be a statement somebody else could take down — which is the one thing it must not be. From that: no update and no delete (the record is the transaction), so no `ver`, no `deleted`, no Deleted tab, no edition chip; no `rate`, no `tRate`; and **no remarks**, since a thread anchored to a declaration is a conversation the declaration cannot answer. There is not even an `op` field — the protocol has exactly one thing you can do, so the data *is* the statement. A builder that emitted `op` out of habit would carve a key the parser never reads and the publisher still pays for, so a test asserts its absence.
>
> **`confirm` is the protocol's own consent gate, and the composer treats it as one.** FEIP8 requires the payload to carry `"This is a formal and irrevocable statement."` and `parseStatement` compares it with `equals` — one wrong capital and the record is ignored with the fee paid. So the phrase is spelled **once**, in the builder, never assembled at a call site; the sheet shows it in full rather than paraphrasing it, because what is ticked should be what is carved; it is never pre-ticked; and **it re-arms on every keystroke in the title or the body**, since a confirmation that survives an edit is confirming words the person did not read.
>
> **The byte budget stops being a formality here.** For a Text the OP_RETURN holds a title, a summary and a 64-character hash, so a novel and a note cost the same. A statement is carved *in full*, uncompressed, which puts the ceiling at roughly a page of prose — the same footing as a `Proof`. The counter is measured off the encoded envelope, Carve is disabled before anything can be paid for, and when the text runs over the sheet says the useful thing rather than just refusing: publish it as a Text, which keeps the body on DISK and carves a hash of it.
>
> **A fourth server-side defect, this one in the mapping.** `statement.json` declared `owner` (wildcard), `active` and `lastHeight` — and **nothing writes any of the three**: the parser writes `publisher`, `title`, `content`, `birthTime` and `birthHeight`, and `rollbackStatement` keys on `birthHeight`. So the field the client filters "Mine" on was absent from the mapping and would have been dynamically typed as analysed text, where an exact `equals` on a mixed-case FID does not reliably match. The mapping now matches what the parser writes, with `publisher` as a `wildcard` like the other five publish indices. **It needs the index recreated to take effect** — a mapping change does not apply to an existing index.
>
> **The "Mine" tab came back empty, and the mapping was why.** `equals` compiles to an Elasticsearch **`terms`** query (`FcdslQueryExecutor.getEqualQuery` → `makeBoolShouldTermsQuery`), which is unanalysed: it matches the token as indexed. Because the mapping never declared `publisher`, every index built from it received the field through **dynamic mapping as analysed text**, whose indexed token is lowercased — so a `terms` query for a mixed-case FID matched nothing, and a FID with statements on chain saw an empty shelf. The corrected mapping fixes it for a freshly built index, but a mapping change does not apply to an existing one, so the client now names **both `publisher` and `publisher.keyword`** in the clause. `equals` ORs its `fields`, a `terms` query against an absent field matches nothing rather than erroring, and the dynamic default gives a `.keyword` subfield holding the FID whole — so one query answers correctly on the deployed index *and* on the reindexed one, in either order. The other five publish mappings declare `publisher` as `wildcard` and need none of this; if one of their Mine tabs ever comes back empty, this is the first thing to check.
>
> **The Publish panes are no longer key-gated.** `WalletPane.needsKey` closed all five for a watch-only identity, on a note that called them "carve forms with no browse mode at all" — true of the placeholders, false the moment this phase shipped. Every one of them opens on a **Discover** tab over the whole chain's shelf, and nothing a published record holds is encrypted, which is the point of publishing. They now browse like Proofs and Tokens, with their compose buttons gated on `canSign` one by one.
>
> **Two smaller notes. (1) Sorting is `birthHeight`, not `lastHeight`** — nothing ever touches a statement again, so the parser never writes a last-anything, and the family's usual sort would have ordered every row on a field none of them have. `EntityProperty` registers the same trap as a *default* sort (`HEIGHT`, `ID`), which is why every query here names its sort explicitly. **(2) The list falls back to the opening line** when a statement has no title, which FEIP8 permits: title-or-content, not both.
>
> **▶ Phase 8.8.3 + 8.8.4 (2026-08-21) — Sound and Video, and the moment duplication stopped paying.** Both ship at once, because **FEIP23, FEIP24 and FEIP25 are one protocol written three times**: same entity fields, same five ops, same lifecycle, same CDD rules, same envelope. What differs is a serial number, a name, an index, and one field spelling — `imageId` / `soundId` / `videoId`. Nothing else, anywhere. So the Image-specific types were **replaced** rather than copied twice: **`MediaKind`** (the configuration), **`MediaRecord`**, **`MediaFeip`**, **`MediaStore`**, media reads on `PublishService`, four kind-taking carves, and **one `PublishMediaView`** serving all three sidebar entries. 1 294 green in FCDomain, app builds, all three panes reachable under Publish.
>
> **This is the opposite call to the one Construct got, and deliberately so.** Phase 8.7 gave Protocol, Service, Code and App four types apiece and said why: "what differed each time was exactly one field." That argument holds when a field differs. Here **no entity field differs at all** — the Java `Image`, `Sound` and `Video` classes are byte-for-byte the same declaration list — so three files would have been three chances for the same code to drift, with nothing to distinguish the copies. Text keeps its own type because it has `type`, Remark because it has `onDid`; those are real differences. Three media protocols are one type with a `kind`.
>
> **The subject key is the entire hazard, so it is defined once and tested everywhere.** A carve naming a `soundId` on the video index is accepted by this client, rejected by the parser, and lost with the fee paid. `MediaKind.subjectKey` derives it, and `MediaCarveTests` runs **every carve against all three kinds**, asserting each writes its own `sn`, its own envelope name and its own subject key — *and the absence of the other two's*. Six tests became eighteen assertions that way.
>
> **`kind` is local bookkeeping, not wire data**, because no media index has such a field — the three are indistinguishable on the wire, and the only thing that knows which is which is the query that was sent. So `PublishService` stamps it on the way out of the index it asked, exactly as it stamps `onChain`, and `MediaStore.upsert` re-stamps from its own namespace on the way in: a row filed in the sounds store is a sound whatever the caller believed. Both directions are tested, because a row that reached a pane claiming the wrong medium would be handed to the wrong player.
>
> **Three namespaces, not one store with a kind column.** `replaceChainRows` deletes what the chain did not return, so a shared namespace would have each kind's refresh wipe the other two.
>
> **What actually differs is presentation, and only that.** An image draws itself; a video draws its first frame through `AVAssetImageGenerator`; a sound draws a waveform glyph, because a black rectangle pretending to be a picture is worse than an honest symbol. In the viewer: `Image(nsImage:)`, AVKit's `VideoPlayer`, and — for sound — a small `AudioPlaybackView` over `AVPlayer` rather than `VideoPlayer`, which would render an audio file as a black box with a transport bar. Thumbnails stay **local-only and off the main actor**, the rule 8.8.2 set: a shelf that fetched every row while scrolling would turn browsing into an unbounded download, and decoding a 40-megapixel photograph into 44 points inline is the one thing a list cannot afford.
>
> **The remark thread needed no work at all**, which is the payoff from extracting it in 8.8.2: `onDid` holds the target's record id, and a record id is a record id whether it names a text, an image, a sound or a video. `RemarkThreadView` took a fourth and fifth caller without a line changing, and `MediaCarveTests` pins that a remark anchors to every kind identically.
>
> **▶ Phase 8.8.2 (2026-08-21) — Image, and the thread that is not written twice.** The second Publish record: **`ImageRecord`** (named for the `SwiftUI.Image` collision, the fourth in this app after `ProtocolSpec`, `AppRecord` and `TextRecord`), **`ImageFeip`** (sn 24 ver 1, five ops, subject `imageId` / `imageIds`), **`ImagesStore`**, image reads on `PublishService`, the file half of `PublishBody`, four carves on `ActiveSession`, and **`PublishImageView`** with its composer and viewer. 27 new tests, **1 291 green in FCDomain**, app builds, pane reachable under Publish.
>
> **FEIP24 is FEIP21 minus one field**, so the argument for having built Text first is that this row cost a day rather than a phase: the tabs, the two queries, the cache rules, the server cursor, the tab-meaning guard, the digest draft id and the byte counter all came across unchanged. The two files stay separate rather than sharing a generic builder, because **the subject field name is exactly what a port copies wrong** — the tests assert `imageId` present *and* `textId` absent on the decoded transaction, and that an image carve contains no `type` beyond the envelope's own `"type":"FEIP"`.
>
> **`RemarkThreadView` was extracted rather than copied.** A remark's target is `onDid`, which this app fills with the target's *record id*, and a record id is a record id whether it names a text, an image, a sound or another remark. So the thread takes an id and nothing else about what it belongs to; the reader sheets differ in how they show a work, not in how they carry a conversation. A second copy is where the two would have started disagreeing about what `onDid` means. `ImageCarveTests` pins that a remark anchors to an image exactly as it does to a text.
>
> **A test caught a real collision in the draft id.** `localId` hashed the bare publish op, and two Publish protocols emit **byte-identical op JSON** for the same title and `did` — nothing in an op says which protocol it belongs to — so a text draft and an image draft with the same fields got the same 64-hex id. They live in separate store namespaces so nothing was corrupted, but the id is meant to identify a draft and a future unified drafts list would have collapsed the pair. All three `localId`s now hash the **envelope**, which carries the `sn`.
>
> **The body is bytes now, not text, and that split `PublishBody` in two.** `fetchURL` is the generic read — the same three attempts (this Mac, our DISK, the publisher's) and the same hash check, with no decode; `read` is `fetchURL` plus a UTF-8 decode, which is also where the "arrived, hashed, isn't text" case stays a final answer rather than a failed attempt. Writing gained `storeFile` / `storeFileLocally`, and **the Phase 8.4 reference-don't-copy decision carries straight through**: a picked file is hashed where it lies and its own path becomes the HAT's location, so publishing a 40 MB photograph costs one hash pass and no duplicate in app storage. There is a test asserting the vault's data directory stays empty for a referenced file.
>
> **What a gallery must not do is fetch as it scrolls.** `ImageThumbnail` draws **only bytes already on this Mac** — a list that pulled every row off DISK would turn browsing into an unbounded download on a pane whose whole premise is that the bytes live elsewhere. Opening a record is what fetches. Decoding is off the main actor and downscaled to three times the drawn side, because rendering a 40-megapixel photograph into 44 points is the one thing a list cannot afford to do inline.
>
> **▶ Phase 8.8 (2026-08-21) — Publish opens, and Text is the first thing in it.** A new phase and a new family: the six FEIPs of the **Publish** category — Statement (8), Text (21), Remark (22), Sound (23), Image (24), Video (25) — which the sidebar has had a heading for since the pane enum was written and which no phase had ever owned. **8.8.1 ships Text and Remark together**, as `TextRecord` / `Remark` / `TextFeip` / `RemarkFeip` / `PublishService` / `TextsStore` / `RemarksStore` / `PublishBody`, eight carves on `ActiveSession`, and a `PublishTextView` that replaces the placeholder pane. 54 new tests (`TextTests`, `PublishCarveTests`, `PublishServiceTests`, `PublishBodyTests`), **1 264 green in FCDomain**, app builds, pane reachable under Publish.
>
> **This is the first feature in the plan with no Android to port.** Every phase before it had an activity to read and a manager to argue with; here there is a protocol spec, a server-side parser, and `FeipClient.text()`, which funnels `OP_FIELDS` through the generic `sendFeip` and decides nothing. So the decisions are ours and are written down rather than inherited — in `PLAN.md` above, and again at the head of the types that implement them.
>
> **The body is not on the chain, and `did` is what it hashes to.** FEIP21 has no content field: a text record is a title, an optional summary and a `did`, and the work lives wherever that points. `did` is opaque to the indexer — a keyword, never dereferenced — so a convention had to be chosen. It is the raw DID, hex `sha256x2` of the body, with the bytes stored on DISK through the Phase 8.4 stack (`FileVault.registerFile` → `HatSyncService.uploadRaw`, a permanent `disk.carve` rather than an expiring `put`). **The point of hashing rather than naming is that the pointer becomes self-verifying**: a location can lie, a hash cannot, so every read hashes what arrived and refuses it unless it matches what the carve committed to. `PublishBodyTests` proves that is load-bearing rather than decorative by having the server substitute the wrong bytes and asserting the read fails.
>
> **Reading is three attempts and the order is the point**: this Mac (a `stat`, because we published it or read it once), our own DISK (the common case on a network with few of them), then the publisher's DISK — resolved through their home map and reached through `dockRegistry`, which is named for the first thing that needed a client-per-server cache but *is* one. Every attempt is recorded and the accumulated reasons travel in the error, because a fetch that quietly finds nothing cannot be diagnosed. One subtlety worth the line it took: **the decode sits outside the retry**, since bytes that arrive, hash correctly and turn out not to be text are a final answer, not a failed attempt — folding that into the loop reported a successfully fetched file as unreachable, which is what the test caught.
>
> **`onDid` is the target's record id, not its `did`.** Both are 64 hex and the field is one keyword, so a client has to pick and stay picked. The txid is what every screen already holds, it exists even for a record published with no `did`, and it makes the anchor uniform across everything remarkable — including another remark, which is what makes a thread. **Remark lives inside the Text module** because it is FEIP21's lifecycle with one field added and one taken away, and `PublishService` serves both indices for the same reason: two clients would be the same query written twice, and the second copy is where the sort keys drift apart.
>
> **Three defects fixed in the reference parser (`FEIP/FeipParser`), and the first one meant the protocol did not work.** (1) **`Text` publish never set `ver`** — `makeText` does not copy it into the history and `parseText` assigned that null onto the entity, so every published row carried `ver: null` and the first `update` raised `NumberFormatException` on `Integer.parseInt` inside a method declared `throws Exception`. `parseRemark`, `parseSound`, `parseImage` and `parseVideo` all hardcode `setVer("1")` at the same point; `parseText` was the only one of the five that did not, which is what makes it a typo rather than a design. (2) **The FEIP6 master bypass was inverted** in all five: on a delete or recover by a non-publisher it loaded the *signer's* `Freer` and required `signer.master == signer`, so the bypass could never fire. It now loads the publisher's and requires `publisher.master == signer`. (3) **`update` clears omitted fields** — documented as intended, so the client resends the record's whole mutable half on every edition, the editor pre-fills from the record for exactly that reason, and `testAnUpdateResendsEveryFieldRatherThanClearingThem` pins it on the decoded transaction. The Java module compiles clean with the three changes.
>
> **What the client tolerates regardless**: `ver` is optional on the way in, decodes from a string *or* a number, and the reader shows "edition —" rather than "edition 1" for a row that has none — rows published before the fix carry null forever, and a reader that trusted the field would show nothing at all while one that defaulted it would claim a first edition it cannot know.
>
> **Four tabs, two queries.** Mine and Deleted are the same publisher-scoped fetch with the `deleted` flag flipped; **Discover drops the publisher clause**, which is the difference between this family and every record family before it — a proof, a protocol or a token is browsed because it is *yours*, and a published work is browsed because it is *anyone's*. Carried over rather than re-derived: the server's own cursor rather than a rebuilt `[lastHeight, id]` (**Android issue C17**), the tab-meaning enforced client-side with a note when the server's filter did not take, the cache owned by exactly one tab, the digest draft id, and the live byte counter with a disabled button before coin selection. New here: **`equals` and `terms` swap slots** depending on whether a publisher was named, since `deleted` and `publisher` are both exact-value clauses and one filter holds one of each kind — the slot conflict `ServiceRegistry` documents, with a test that both survive one request because dropping either silently widens the result.
>
> **A draft keeps its body in the HAT store under the DID it will publish as.** `TextRecord` has nowhere to put text because FEIP21 has no content field, so `PublishBody.storeLocally` registers the bytes without uploading: a draft and its published form are the same bytes in the same place, saving and reopening never re-derive them, and nothing is paid for until somebody chooses to publish. On publish the upload happens **before** the carve is built, so a publish that cannot reach a DISK fails while it is still free — carving a pointer to bytes nobody can fetch costs a fee and produces a permanent dead link.
>
> **`rate` is built and not wired**, exactly where 8.7.5 left it for the Construct four: the op builders and the `tRate` / `tCdd` display ship, the action waits for weight-aware coin selection. The floor is 1 CD, which the carve path already guarantees — what is deferred is control over the *weight*, not the ability to rate. The carve tests run with `bestHeight` past `cddCheckHeight` and an aged cash, so they exercise the coin-day rule rather than dodging it.
>
> **▶ Phase 8.7 (2026-08-18) — Construct, the four records that say what the network is made of.** This phase exists because a reviewer asked why Protocol wasn't in the plan, and the honest answer was worse than "we forgot": **Protocol, Service, Code and App are one family and this document had never said so.** `protocol` and `application` were two words buried in row 8.3's four-item list, `Service` existed only as `Directory/Service.swift` — a read-only model for turning a SID into a URL, with no lifecycle at all — and `Code` appeared nowhere in 470 lines of plan. Between them they are **~20 000 lines of Android across thirty activities and four ~600-line managers**, and every one of those thirty activities is the same eight: browse, create, update, stop, stopped, recover, close, hidden. Porting any one of them alone would have meant building that lifecycle four times and discovering the shared shape on the fourth. So they get a phase, and a **sidebar heading of their own** — the Construct — because the distinction they draw is real: Mail, Chat, Files and Tokens are things that pass *through* the network; a protocol, its implementation, a running instance of it and an installable app are what the network is *made of*.
>
> **8.7.1 — Protocol.** Ships as **`ProtocolSpec`** (field-for-field with the Java model), **`ProtocolFeip`** (sn 1 ver 7, protocol name `FeipProtocol` — the six ops `publish` / `update` / `stop` / `recover` / `close` / `rate`), **`ProtocolService`** (`base.search` over entity `protocol`, plus the by-ids reader), **`ProtocolsStore`**, five carves on `ActiveSession`, and a **`ProtocolsView`** pane with its publish/update, detail and close sheets. 56 new tests (`ProtocolTests`, `ProtocolServiceTests`, `ProtocolCarveTests`), 870 green in FCDomain, app builds and the pane is reachable from the sidebar.
>
> **8.7.3 — Code, taken out of order.** Row 8.7.3 always said Code was "closest of the four to Protocol", and that turned out to be the reason to ship it second rather than third: **Service grows an existing read-only model and App collides with a SwiftUI protocol, while Code is Protocol's shape with a different index.** It lands as **`Code`** (field-for-field with the Java model), **`CodeFeip`** (sn 2 ver 1, protocol name `Code` — the six ops `publish` / `update` / `stop` / `recover` / `close` / `rate`), **`CodeService`** (`base.search` over entity `code`, plus the by-ids reader), **`CodesStore`**, five carves on `ActiveSession`, and a **`CodesView`** pane with its publish/update, detail and close sheets. 62 new tests (`CodeTests`, `CodeServiceTests`, `CodeCarveTests`), 932 green in FCDomain, app builds and the pane is reachable from the sidebar under Construct.
>
> **What a code record is, and the one field that makes the pane different.** A protocol record registers a *specification*; a code record registers an *implementation* of one — this program, this version, written in these languages, fetchable from here. The chain holds the claim and the artefact's DID, never the code. The field with no analogue in Protocol is **`protocols`**: the list of specification record ids this implementation claims to speak, which is the edge between the first two Construct records. It is **picked from the live protocol registry** rather than only typed (Android binds the same picker), because each entry is 64 hex characters that nothing validates — a mistyped one leaves a record claiming to implement a protocol that does not exist — and the ids already on a record are resolved back to names in both the editor and the detail sheet. Three smaller field differences: no `type`, no `sn` and no `prePid` (an implementation is not numbered by FEIP and does not supersede in place, it bumps `ver`); `langs` is a *list* where a protocol has one `lang`, because a spec is written in one natural language and an implementation in several programming ones; and there is **no `birthTxId`**, which the Java model also omits — a code record's id *is* its publish txid, so a second copy could only agree or be wrong.
>
> **Three things worth writing down. (1) The subject field is `codeId`, not `pid`.** The two records are otherwise the same shape, which makes the one field that differs exactly what a port copies wrong; it is asserted on the decoded raw transaction in `CodeCarveTests`, not just on the builder. **(2) Android issue C20 is *absent* here, and the absence is pinned.** `ProtocolOpData.rate` is a primitive `int`, so Gson writes `"rate":0` into every protocol op Android sends; `CodeOpData.rate` is a boxed `Integer` and stays null. The same bug is one keyword away in the file next door, so `testNoOpCarriesAStrayRateField` guards the good copy. **(3) The byte budget bites sooner than Protocol's.** Four protocol ids are a quarter of the OP_RETURN before a word of description is typed, so the live counter and the disabled Publish button matter more here than they did there, and an oversize protocol list is refused before coin selection alongside an oversize description.
>
> **8.7.2 — Service, the record that was already half here.** Row 8.7.2 said "not a fresh model", and that turned out to be the whole shape of the phase: `Directory/Service.swift` has read this index since Phase 9.2.4b for SID→URL discovery — `HomeServiceResolver` resolves every `(sid)` in a `home` map through it, which is how a message finds a DOCK — so the lifecycle half was **grown onto that model in place** rather than shipped as a second `ServiceRecord` next to it. Two types over one index would have meant two decoders disagreeing about what a service is, on a path where being wrong stops messages moving. It lands as the grown **`Service`** (now field-for-field with the Java model, thirteen pricing fields included), **`ServiceFeip`** (sn 5 ver 3, protocol name `Service` — the six ops `publish` / `update` / `stop` / `recover` / `close` / `rate`), **`ServiceRegistry`** (`base.search` over entity `service`, plus the by-ids reader), **`ServicesStore`**, five carves on `ActiveSession`, and a **`ServicesView`** pane with its publish/update, detail and close sheets. 70 new tests (`ServiceRecordTests`, `ServiceRegistryTests`, `ServiceCarveTests`), **1 002 green in FCDomain**, app builds and the pane is reachable from the sidebar under Construct, between Protocol and Code.
>
> **What a service is, and the three things it has that the other two do not.** A protocol registers a specification, a code record registers an implementation of one, and a service registers **an implementation somebody is actually running at an address** — the end of that chain of claims. So: (1) it is **reachable**, and the endpoint under `home["API"]` is on the row, copyable, with a warning in the editor and the detail sheet when the map has no `API` key at all, because a home map without one resolves to no URL and fails silently at the far end; (2) it has a **component list**, which is what every picker on the network filters on — Files searches `DISK@No1_NrC7`, the message path searches `DOCK@No1_NrC7`, matched by *exact value* — so the pane gets a component filter of its own next to the state filter, and the editor offers the four well-known names as one-click chips rather than trusting a comma-separated field; and (3) it has **thirteen pricing fields**, flat on the wire next to `stdName`, behind a disclosure in the sheet and summarised to one headline figure on the row. Naming is the other difference: a service has `stdName` plus a `localNames` language map where the other three have a plain `name`.
>
> **Four things worth writing down. (1) The subject field is `sid`** — `pid`, `codeId`, `sid`, one per record, and the field a port copies wrong; asserted on the decoded raw transaction, with `pid` and `codeId` asserted *absent*. **(2) The pricing fields are flat, not nested.** Java has a `params` object that looks exactly like where they would live; they were moved out of it and it is now always null, so this builder does not emit `params` at all. **(3) `minCredit` is reachable here and is not in Android** — it is declared on both the model and the op data, and no input in either activity ever writes it. **(4) `type` is free text, and Java's enum is a trap.** `Service.ServiceType` has four constants and `valueOf` is called on whatever the user typed, so anything else throws — *including* the `FAPI@No1_NrC7` spelling the chain actually stores, because `valueOf` wants the underscore form. Worse, `UpdateServiceActivity` fills the field from `fetchServiceType().name()`, which is `OTHER` for anything unrecognised: **updating a service whose type Java does not know rewrites that type to `OTHER`.** Here it is a string with a suggestions menu, and it round-trips whatever the chain holds. Call the crash and the silent rewrite **Android issue C22**.
>
> **The byte budget is tightest on this record of the four.** A service can name five id lists (`components`, `waiters`, `protocols`, `codes`, `services`), two maps and thirteen prices into one uncompressed OP_RETURN, and protocol and code ids are 64 hex characters each — four of each is 550-odd bytes before a word of prose. The live counter, the disabled Publish button and the pre-broadcast guard all matter more here than they did on Protocol or Code, and `testAnOversizeIdListIsRefusedBeforeBroadcast` pins the list case separately from the description case.
>
> **One fcdsl detail that is not in the other two.** `active` goes in the query and `closed` in the top-level `filter`, as before — but this pane has a *third* clause, the component, and one filter holds one clause of each kind. So the component takes `terms` (the shape `DirectoryService` has used for the DOCK and DISK pickers since they shipped) and `closed` moves to `equals` when both are asked for. Both are exact-value clauses and `Filter extends FcQuery` in Java, so both keys are available; it is a slot conflict, not a semantic choice, and there is a test that both survive the same request because dropping either silently widens the result.
>
> **Two caches over one index, kept apart on purpose.** `ServicesStore` holds the pane's registry window; `HomeServiceResolver` holds resolved SID→URL answers for the message path. They read the same rows and cache different things for different reasons, and neither is made to serve the other — a browse that evicted the resolver's DOCK would stop messages moving. There is a test asserting a row saved to the pane's window is *not* visible as a resolution answer.
>
> **8.7.4 — App, and the Construct family closes.** The last of the four, and the one whose row had a warning on it from the day the phase was written: **name it something other than `App`**, because SwiftUI's `App` protocol is in scope in every view file. It ships as **`AppRecord`** (field-for-family with the Java model, `Download` nested inside it), **`AppFeip`** (sn 15 ver 1, protocol name `APP` — the six ops `publish` / `update` / `stop` / `recover` / `close` / `rate`), **`AppService`** (`base.search` over entity `app`, plus the by-ids reader), **`AppsStore`**, five carves on `ActiveSession`, and an **`AppsView`** pane with its publish/update, detail and close sheets. 70 new tests (`AppRecordTests`, `AppServiceTests`, `AppCarveTests`), **1 072 green in FCDomain**, app builds and the pane is reachable from the sidebar under Construct — which now holds all four records the heading was created for.
>
> **The name on the wire is `APP`, in capitals, and that is not cosmetic.** The other three are `FeipProtocol`, `Code` and `Service` — title case, spelled the way the Swift type is — so `App` is exactly what a port writes, the envelope would carry a protocol name no indexer matches, and the record would simply never appear. `AppFeip.protocolName` reads it from the `FeipProtocol` registry rather than spelling it locally, and a test asserts it is `"APP"` **and** not `"App"`.
>
> **The field that makes the pane is `downloads`, and Android does not have it.** It is a list of `{os, link, did}` objects — the only nested structure anywhere in the Construct family — so one record can offer a build per platform with a digest to check each against. `CreateAppActivity` and `UpdateAppActivity` both pass `null` where downloads go, commented "not implemented in this UI", and `AppActivity` displays nothing. Two consequences, and the second is the serious one: an app published from Android **cannot say where to get it**, and because an update resends the record's whole mutable half, an app updated from Android **erases whatever downloads another client carved**. Call it **Android issue C23**. Here downloads get a proper row editor, the list rides every update, the pane shows a chip per platform — green when the build carries a digest, orange when it does not, because a link nobody can verify is worth flagging on the row rather than burying in a sheet — and `testAnUpdateResendsTheDownloadsRatherThanClearingThem` pins it on the decoded transaction.
>
> **Three smaller notes. (1) The subject field is `aid`** — four records, four spellings (`pid`, `codeId`, `sid`, `aid`), and the one thing a port copies wrong; the update test asserts the other three are *absent* from the raw transaction. **(2) `types` is a list** where a service has one `type`, because an app is often several things at once, so the narrowing is a `terms` clause against the list and it shares the filter slot with `closed` the same way Service's component does. **(3) `downloads` is not searchable and that is the index's choice** — Java does not list it either, since `match` scores text and this is a list of objects. `AppRecord.matches(query:)` does reach into it, so a download link is findable among loaded rows, just not chain-wide; `AppService.Field.searchable` says so where someone would look for it.
>
> **What the family cost, and what it came to.** Four records, ~20 000 lines of Android across thirty activities and four ~600-line managers, ships as four panes over twelve domain types and 258 tests. The shape held: after Protocol, each of the three that followed reused the state filter, the `filter`-is-a-sibling-of-`query` placement, the server cursor (**C17**), the digest draft id, the paired `home` editor (**C21**) and the pre-broadcast byte guard without re-deriving any of them. What differed each time was exactly one field — Code's `protocols`, Service's `home`+prices, App's `downloads` — which is the argument for having made it a phase rather than four unrelated ports.
>
> **Carried over from 8.7.1 rather than re-derived**, because Code is the same lifecycle: the four-way state filter (Live / Stopped / Closed / All) where Android's list is hardwired to `active = true` and its `StoppedCodeActivity` to the complement, so a closed record is reachable from neither; `active` in the query and `closed` in the top-level `filter`, since one `terms` naming two fields matches either value in either field; paging from the server's own cursor rather than Android's rebuilt `[lastHeight, id]` (**Android issue C17**); a draft id that is a digest of the payload it will carve rather than `"local_" + currentTimeMillis()`, and one that does not write `active = true` on a record no chain has seen; and `home` edited as label/URL *pairs* rather than a comma-separated `key:value` string that splits `https://example.com` at the scheme (**Android issue C21** — `CreateCodeActivity.parseUrlMap` has it too, with an `=` fallback that does not help). `langs` keeps Android's single comma-separated field, because a list of language names has nothing in it a comma can be confused with — but the parse is echoed back as chips, so what will be carved is never a guess the user cannot see. Not ported: the `rate` op (built and tested, still 8.7.5) and the tri-state client-side sort buttons.
>
> **Two names had to give way, and it is worth writing down why.** The record is **`ProtocolSpec`, not `Protocol`**: `Protocol` is a class in `ObjectiveC`, which Foundation re-exports, so the type would be ambiguous in every file importing both — and `FeipProtocol` was already taken by the sn→name registry from 8.6, which this record's `sn` field is emphatically *not*. That second collision is not cosmetic: **a protocol record registering FEIP-12 carries `"sn":"12"` inside an envelope whose `sn` is `"1"`.** Two different numbers with the same name in one carve; the model, the builder and the tests each say so out loud. 8.7.4 will hit the same wall with `App` against SwiftUI's `App` protocol, which is why its row says so now rather than after it is written.
>
> **The registry is chain-wide, and that changes the pane's shape.** A proof list is yours by construction — `ProofService` scopes every query to your FID, because a pane titled "your proofs" that returned strangers' documents would be a different feature wearing this one's UI. A registry is worth having for exactly the opposite reason. So Registry browses the whole index unscoped, **Mine** is the filter you opt into (Android's More ▸ My protocols), and the cache is written only by the unscoped live browse — caching a Mine page would overwrite a four-hundred-row window with the four rows you happen to own, and the next offline open would show four.
>
> **Stop is not close, and the app is built around the difference.** `stop` takes a protocol out of force and `recover` puts it back; `close` retires it and nothing reopens it. So `ProtocolSpec.state` is one value rather than three booleans read in the right order (`closed` outranks `active`, and a list that checks them the other way round shows a closed protocol as live), `canRecover` is false for a closed record so the button cannot spend a miner fee on a no-op, and Close gets a sheet with a statement field and a plain warning while Stop and Recover get alerts.
>
> **Four divergences, each deliberate. (1) A state filter that can see everything.** Android's list is hardwired to `active = true` and its `StoppedProtocolActivity` to the complement — so **a closed protocol is reachable from neither**, which is 753 lines spent on a view that cannot show one of the three states. Here it is a four-way picker (Live / Stopped / Closed / All) on both chain tabs. Note the two flags cannot share one `terms` clause: naming two fields and two values matches either value in either field, so `active=true, closed=false` asked that way returns precisely the rows it excludes — `closed` goes in the top-level `filter`, which is a *sibling* of `query` in the fcdsl, not a member of it. **(2) Search pages from the server's cursor.** `buildSearchFcdsl` rebuilds `after` as `[lastHeight, id]` whatever it sorted by, and worse, `addSortingToFcdsl` defaults to sorting on `lastTime` while `makeSortList` builds the cursor from `lastHeight` — so even its *default* search pages against keys it is not sorted on (**Android issue C17** again, in its sharpest form yet). **(3) A draft keeps its row.** Android ids a local record `"local_" + currentTimeMillis()`, so saving the same draft twice leaves two rows and three times leaves three; the id here is a digest of the payload the publish will carve, so an unchanged draft is stable across a reload and an edited one moves deliberately. It also does not write `active = true` on a record no chain has seen — `active` is the indexer's verdict, and `state` reads `.draft` off `onChain` instead. **(4) The home map is edited as pairs.** Android takes label→URL as one comma-separated `key:value` text field and splits on `indexOf(':')`, which cuts `https://example.com` at the scheme: any URL typed without a label becomes the key `https` pointing at `//example.com` (**Android issue C21**). Two fields per row cannot be ambiguous about which half is which.
>
> **Also not ported, and one thing added.** The `rate` op is built and tested but nothing calls it — a rating's weight is the coin-days its transaction destroys, so the carve needs manual coin selection against the wallet's spendable set; that is a wallet feature serving five entity types, and it is 8.7.5 rather than a quarter-built corner of this one. Android's `"rate":0`, which Gson writes into every publish, update, stop, close and recover because `ProtocolOpData.rate` is a primitive `int`, is not sent — a field those ops do not define, on a payload capped at 4096 bytes (**Android issue C20**). The tri-state client-side sort buttons are gone for the reason they went in News and Proof. What is new is the live byte budget: the registration goes into an OP_RETURN uncompressed and unencrypted, the ceiling is reached by an ordinary paragraph plus a handful of waiters, and Android checks nothing at all — you fill the form, press Publish, and the transaction fails at broadcast.
>
> **▶ Phase 8.3b-i (2026-08-18) — Token, the ledger the chain keeps for you.** Row 8.3's four-word list hid Proof; the word next to it hid **six thousand lines** of Android token code — nine activities (`TokensActivity`, `MyTokenActivity`, `CreateTokenActivity`, `IssueTokenActivity`, `SendTokenActivity`, `CloseTokenActivity`, `TokenHistoryActivity`, `HiddenTokenActivity`, `HiddenTokenHolderActivity`), an 880-line `TokenManager`, and two card containers. Token has no dependency on application or protocol, so it ships alone as **8.3b-i**, leaving those two as **8.3b-ii**. It lands as **`Token`**, **`TokenHolder`** and **`TokenHistory`** (field-for-field with the Java models), **`TokenFeip`** (sn 20 ver 1 — the five ops `deploy` / `issue` / `transfer` / `destroy` / `close`), **`TokenService`** (`base.search` over *three* indices — `token`, `token_holder`, `token_history` — plus the by-ids reader), **`TokensStore`**, five carves on `ActiveSession`, and a **`TokensView`** pane with its deploy / issue / send / detail sheets.
>
> **Three indices is why it is three tabs and not three filters.** Holdings is `token_holder` scoped to the live FID — what you can actually spend. Tokens is the chain-wide `token` index — every ledger that exists, including the ones you have no stake in, because that is how you find one. History is `token_history`, the op stream the other two are *derived* from. Android splits these across seven activities carrying three separate copies of the same paging, sorting and hide logic; the queries differ, the machinery does not.
>
> **Holdings needs a second fetch and it is not optional.** A `token_holder` row carries a `tokenId`, a balance and nothing else — no name, no decimal scale, no closed flag. A balance cannot be *formatted* until its token is resolved, let alone spent, so every holdings refresh follows up with a by-ids batch over the tokens it mentions; the pane says so when a row is still unresolved rather than rendering a bare hex id with the decimal point in the wrong place.
>
> **The amounts are digits all the way to the OP_RETURN.** Android parses a typed amount into a `double` and lets Gson print whatever that rounds to — so asking to send `0.1` can sign a carve that says something else. `TokenTransfer` holds the user's own digits as text, validates them against the token's declared scale (which the parser enforces, and which is the difference between a message and a wasted miner fee), and serialises through `NSDecimalNumber`, the one numeric type `JSONSerialization` writes out digit-for-digit. Trailing zeros normalise (`1.50` → `1.5`); nothing else is rewritten.
>
> **Four verbs that sound alike and are not.** *Close* retires a token for everybody, permanently, and only its deployer can, and only if it was deployed `closable`. *Destroy* burns the signer's own balance — the op takes an id, not an amount, so there is no partial burn and the confirmation says the whole balance out loud. *Hide* is local to this Mac, carves nothing, and another device will still show the row. And a token *transfer* — unlike a proof transfer, where the payment output **is** the addressing — names its recipients in the payload and pays them no FCH at all: the corollary is that a transfer to a FID that never existed is a carve that succeeds and moves value nowhere, so the recipient is checked by the form because the chain will not check it.
>
> **The rules are immutable, and the deploy sheet is the last point at which they exist as anything but history.** `transferable`, `closable`, `openIssue`, the cap, the scale and the three issue limits are fixed by the deploy carve; there is no op to change any of them. The one thing that moves afterwards is `closed`, in one direction. There is also no draft: a token's id *is* its deploy transaction, so a token that has not been carved does not exist to be drafted — Android says the same thing via a Save button whose only behaviour is to explain that tokens must be published on-chain.
>
> Two Android defects do not come across. **C17 again** — `searchTokensFromApi` rebuilds `after` as `[lastHeight, id]` for every search whatever it sorted by, so its name-, deployer- and circulating-sorted searches page wrong; `TokenService` feeds the server's own cursor back instead. And **the deploy carve keeps rules the parser ignores**: Android drops the three issue limits when `openIssue` is false in `CreateTokenActivity` but nowhere else, so `TokenFeip.deployOp` enforces it at the builder, where a rule that nothing will ever enforce cannot reach the permanent record.

> **What Android has that this doesn't.** `HiddenTokenActivity` and `HiddenTokenHolderActivity` are two separate screens for un-hiding two kinds of row; here hiding is a toggle in the toolbar that flips either list to show what was hidden, because "the hidden ones" is a filter over a list, not a different list. `TokenHistoryActivity` becomes the third tab plus the detail sheet's History tab — the same index, scoped by party or by token. And the tri-state client-side sort buttons are gone for the reason they went in News and Proof: sorting the visible window by a key the server is not paging on makes Load-more append rows in the wrong place. 64 new tests (`TokenTests`, `TokenCarveTests`, `TokenServiceTests`, `TokensStoreTests`), 814 green in FCDomain, app builds and the pane is reachable from the sidebar.

> **▶ Phase 8.3a (2026-08-18) — Proof, the one record meant to be shown.** Row 8.3 has said "application / token / proof / protocol lifecycle" since this document was written, and behind that one word sat four Android activities and 2 145 lines: `IssueProofActivity`, `ProofActivity`, `DestroyProofActivity`, `ProofDestroyedActivity`, plus `ProofManager` and `ProofCardContainer`. > **This is the app's only feature with no cipher anywhere in it,** and that is the point rather than an omission: a proof you cannot hand to someone who distrusts you proves nothing. Everything else the app carves is either encrypted to a pubkey (mail, contacts, secrets) or a statement about the carver (notice fee, home). A proof is a statement *for third parties*, and every consequence below follows from that. It reads without a key, so like News it works fully on a watch-only identity — you can watch a proof you were invited to countersign from a FID you cannot sign with; what you cannot do from there is countersign it, because **the carve's own signature is the countersignature** and there is no key to make one with.
>
> **Three roles, one query.** The chain clause matches your FID against `owner`, `issuer` *and* `cosignersInvited` at once — proofs you hold, proofs you minted and gave away, and proofs somebody else minted and asked you to sign. (1) A byte budget, live, on the encoded envelope.** A proof's text goes into an OP_RETURN uncompressed and unencrypted, so the 4096-byte ceiling is reached by ordinary prose. > **▶ Phase 7.10 (2026-08-19) — what you sign, and what you can spend the second after you sign it.** Two Android behaviours the Mac was missing, both about the moment a transaction leaves the wallet. **(1) A confirmation gate over every signing path.** Android has `Setting.userConfirmTx` (default true) and a whole review activity, `SendTxActivity`, that a payment passes through; the Mac had a per-pane "are you sure" alert on Send and *nothing at all* on the twenty-odd carves that panes make on the user's behalf — a contact edit, a mail, a chat key rotation, a token issue all signed and broadcast without ever showing the transaction. > **▶ Phase 9.3 (2026-08-20) — Compose: the transaction you build yourself.** Android's `CreateTxActivity` (2 054 lines) had no Mac counterpart and no row in this plan. **Send is not a subset of it.** Send asks two questions and decides the rest — which coins, how many outputs, what the change looks like — which is right for almost every payment and wrong for the ones this pane exists for: paying twelve people at once, spending one particular cash, writing a message alongside a payment, or locking a payment until a block height. Conflating them locks money somewhere nobody meant, so the two are separate properties with a test each. **`TxFee` is a second fee model on purpose.** `CoinSelector` prices a P2PKH payment while it is still choosing coins; `TxFee` prices a transaction the user already composed, where the size depends on script shapes that only exist once the outputs do. And `rest == −34 → 0` is a leftover from a fee calculator that always priced a change output: against the current one it only fires on a genuine 34-satoshi shortfall, where it would report a balanced transaction the builder then refuses, so the pane reports the real remainder and "spend the rest" is answered exactly instead — `maxValueForOutput` prices the transaction *with* the candidate at a value that rules out change and subtracts, which is right for every output shape rather than Android's fee-delta-minus-a-hardcoded-change-cost. **Multisig inputs are refused, not half-signed**: they need every member's signature and a merge step, and one key's attempt would produce a transaction the chain rejects — so the composed path signs P2PKH and single-sig CLTV and says why for the rest. `tools/vector-gen` now compiles the real FC-AJDK `P2SH` and `TxHandler` on a plain JVM (one Jackson marker stubbed), so the script encoding, the P2SH addresses, the manifest JSON and eight fee shapes are checked against the code Android runs rather than against a reading of it. 53 tests (14 `P2sh`, 8 `TxFee`, 15 `AdvancedTxBuilder`, 16 `WalletService`), FCCore 175 + FCDomain 1 182 green, `tools/sidebar-check` clean. **Two UI faults found by looking at it, both of a kind the compiler cannot see.** `person.crop.circle.badge.magnifyingglass` does not exist in this SDK, and SwiftUI draws a name it cannot resolve as *nothing* — so every "find a FID" button in the app was a blank bordered rectangle, in **eight** places, none of them new to this phase. `tools/symbol-check` now resolves every `systemName:` / `systemImage:` literal in the app against `NSImage` (111 symbols, 395 uses) and fails on one that does not exist; the answer is a runtime fact about the OS, which is why nothing upstream of it could help. > **▶ Phase 9.2.6 (2026-08-14).** The two on-chain flavours, and the point of them is that **the membership is not ours to decide**. > **▶ Phase 9.2.5 (2026-08-14).** Rooms. **Nothing about a room is on the chain** — no carve to look up, no indexed member list, no way for a stranger to enumerate one, and equally **no arbiter**. The owner's copy *is* the membership and everyone else holds a cache of what the owner last told them, which is why every inbound rule in `RoomService` is an owner check and why the check is never "the message says it is from the owner": a `RoomInfo` payload carries an `owner` field its sender wrote. The rule is "the sender is the owner **of the room we already have**", and for a room we do not have there is nothing to check against — which is exactly why accepting an invitation is a decision only a person makes, and why `handle` returns `.invitation` rather than joining. That gap is a live hole in Android: a `RoomInfo` naming an existing room id with the sender as `owner` satisfies `isFromOwner`, gets rejected by the member check, and *still* raises a room-invite prompt; accepting it overwrites the room's owner, member list and stored symkey. Logged as Android issue **C12**; `acceptInvite` here throws `invitationOwnerMismatch` and stores shared keys with `allowOverwrite: false`. **`RoomService` returns messages rather than sending them** — the same split `DeliveryPolicy` uses — so the whole protocol, which is where a room's security lives, is testable with no network. **Removal rotates the key, and that is the operation**: a removed member keeps every key they ever held and everything those keys open, so removal can only mean "from here on" and without the rotation it would mean nothing at all; a member *leaving* forces the same rotation, minus the redundant "you are out". Disbanding **keeps** the keys — it ends the conversation, it does not burn the transcript. Room control traffic travels **P2P**, not on the room's channel, because an invitation must reach someone not yet in the room and a removal must reach someone no longer in it. Two model decisions: the room id keeps Android's `room_`-prefixed shape and therefore **contains an underscore**, which is why 9.2.3's symkey storage key parses on the *last* one; and `Room.symkeyVersion` means "what the owner last announced" while `SymkeyStore` means "what we can actually decrypt with" — genuinely two facts, and the gap between them is the cue to go and ask for a key. `GsonCompatibleWriter` gains `.stringMap` (keys sorted — Gson writes a `HashMap` in unspecified order, so parity is not on offer at any price). 28 tests.

> **▶ Phase 9.2.4a (2026-08-14).** The delivery machinery — everything that decides what to do with a message, with no transport under it. **9.2.4 is now 4a and 4b**, and the reason is worth stating rather than discovering later: the deciding half is testable today, while the wiring needs three things the port does not have — home→service resolution (`Freer.home` is decoded, but nothing reads a service out of it), a FUDP node that dials **by FID** (Phase 4 built the initiator side; `FudpClient` dials a known host:port and `ConnectionManager` indexes *inbound* connections, so nothing turns a peer FID into an endpoint), and DOCK/ROAD clients. Building the machinery against a transport that does not exist yet would have meant guessing at its shape twice. The **`MessageQueue` is a store, not a loop**: Android's owns two executors and a 30-second ticker, while this answers only "what is due" and "what does this outcome mean", so both are testable without a clock or a network — and it is durable, because the alternative is that quitting between "send" and "sent" drops a message silently. `SendResult` is three-way for a reason that shows up in the tests: a peer being asleep and a target FID being nonsense both look like "it didn't send", and conflating them means either giving up on someone who will be back or retrying a malformed message every fifteen minutes forever. The backoff walks all five steps — Android's reads the array *after* incrementing, so its 5 s entry is dead code and its first retry waits 15 s (logged as Android issue **C11**); nothing on the wire depends on the schedule, so we use the one the array plainly describes. **`DeliveryPolicy`** lifts the route order out of `P2pHandler.sendP2p` into a pure function: direct, then relay, then the recipient's own DOCK, then ours — an order of *preference*, not of likelihood, since the first two only work for someone who is online and the third is the only one that works for someone who is not. An empty plan is a **permanent** failure (no address is not a network problem), while a plan whose routes all failed is transient. **Receipts only ever advance a status.** Delivery is unordered, so a `delivered` receipt can arrive after the `read` that followed it, and applying receipts in arrival order would flip a message the recipient has already read back to merely delivered; a read receipt also stamps the delivery time, because a peer who reads on sight sends one receipt and not two. **`PeerBook` presence is a question about age, not a stored flag** — nothing tells us when someone leaves, since a peer closing their laptop sends no goodbye — and a DOCK delivery deliberately does *not* refresh it: storing a message for someone is evidence they were **not** reachable, and counting it as a sighting would keep the direct route at the front of the plan forever. 23 tests.

> **▶ Phase 9.2.3 (2026-08-14).** The keys group traffic is sealed with. **Every version is kept forever** — a rotation *adds* a key rather than replacing one, because messages already sealed under v3 still have to open after the room moves to v4 and this store holds the only copy of v3. So "the room's key" always means the newest version, while decryption always asks for the version the message names, and `SymkeyStore.open` reaches for that one rather than the current one. **A received key never overwrites one we hold** unless the caller vouches that the sender is the entity's owner: without that rule any member could push a bogus key for an existing version and make everyone's history unreadable. The store cannot know who the owner is — that lives with `Room`/`Team` in 9.2.5/9.2.6 — so it takes the answer as an argument and makes the caller state it, and refusing an overwrite is an ordinary `false`, not an error, since two members answering the same request is the normal case. Non-positive versions are refused, and that guard is real rather than decorative: `symkeyVersion` is a 64-bit field the wire carries in **32** bits and sign-extends coming back (9.2.1), so a peer genuinely can name a negative version, and storing a key there would put it where no honest rotation could reach. **We store the key itself; Android stores it sealed** — Android wraps each key AsyOneWay under the user's own pubkey because on that platform the row has only the app sandbox behind it, while here the row is already AES-GCM under a vault key that is `HKDF(configure symkey, …)`, derived from the very password that releases the identity privkey. Same gate twice buys nothing and would cost an ECDH per message decrypted; not having it is why this store needs no in-memory key cache and Android's does. P2P bodies reuse 9.1.1's AsyTwoWay so the sender can reread their own messages, with the note-to-self AsyOneWay exception `Mail` already needed. > **▶ Phase 9.2.2 (2026-08-14).** Where messages live. Chat history is **the first collection in this app with no ceiling** — every other store is human-scale and can answer `all()`, which is exactly what `TypedStore`'s own doc comment warns against here — so `MessagesStore` is shaped around never loading what it is not showing: **one `EncryptedKVStore` namespace per conversation** (`im.messages.v1.<threadId>`, so opening one chat never touches another's rows) and a key of **zero-padded timestamp + message id**, which makes SQLite's `ORDER BY key` the transcript's own order and paging a slice of a string array — no ciphertext is decrypted until a row is actually wanted. 19 digits is `Int64.max`, so every timestamp pads to the same width and text order is numeric order; a negative timestamp clamps rather than wrapping into a shorter string that would sort in the wrong place. `page(before:limit:)` walks backwards the way a chat view scrolls, and a nil `olderCursor` doubles as "no more". The cost of the shape is that find-by-id is a scan of that conversation's *keys* (never its values) — bounded and cheap, but not an index, and the note says when to add one. **Bodies are stored open when they could be opened** — the deliberate opposite of `MailsStore`: a mail's cipher can always be reopened with the identity key, while an IM cipher is an ephemeral transport wrapper whose symkey version may be rotated away, so keeping it would mean holding a blob that goes unreadable while the plaintext beside it stays fine; the cipher is kept only for a message we could *not* open, where it is the sole copy. The store also refuses to name a message (`put` throws without an id) because ids belong to the FUDP layer, and `mutate` re-puts under the *original* key so a status change cannot move a message in the transcript. `ConversationsStore` is the index over it, human-scale and explicitly **a cache**: `rebuild(id:from:)` recovers every field from the messages, which is what makes optimistic updates on the delivery path safe. Two judgment calls beyond the port: an older message arriving late (DOCK backlog after a direct send) counts as unread and moves the thread's birthday back but does **not** rewrite the preview, and `ContentType.isDisplayable` keeps signals out of the unread count — otherwise a peer could hold a conversation at the top of the list by typing at it forever. > **▶ Phase 9.2.1 (2026-08-14) — opens Phase 9.2 (IM).** `ImMessage` and the five enums it routes on. The phase breakdown is new too: 9.2 was five bullets and is now seven sub-phases, ordered bottom-up (message → store → key → delivery → groups → pane) so each layer is testable without the one above it. **An IM message has two serializations and they disagree on purpose.** `wireJson()` is the local-storage form and carries everything, including this device's delivery bookkeeping; it also crosses devices, because a HISTORY share writes one line of it per message into a file the other client reads back — so Gson's rules bind here exactly as they do for `Mail`: declaration order, nulls omitted, HTML escaping off, enums **by name**. `toWireBytes()` is what actually travels, and it carries only what the recipient could possibly know — no `status`, no `roadIds`, no `dockId`, no `readAt`, no `unread`, no `sequence` — because those describe *our* relationship to the message and a port that preserved them would be handing the receiver invented facts about itself. On the wire the same enums go **by ordinal**, which is the sharp edge of the whole sub-phase: a transposed case keeps every JSON test green while silently re-labelling every message (a `VOICE` arriving as a `ROOM_LEAVE`), so `JavaOrdinalEnum` derives the ordinal from declaration order rather than restating it and the vectors pin all 43 constants by number. Three lossy behaviours are **reproduced, not repaired**: `symkeyVersion` is a Long the wire carries in 32 bits (a version past 2³¹ arrives sign-extended and negative), a nil `type`/`contentType` writes ordinal 0 and so arrives as `P2P`/`TEXT`, and empty-vs-nil is indistinguishable for the length-prefixed strings. Widening any of them would just be a different protocol. Unlike `Mail` and `Hat`, **the id is not derived** — it is the FUDP layer's 64-bit message id in 16 hex chars, over the *bit pattern* (half of all ids are negative), and Java's `getId()` override exists solely to stop `FcEntity` auto-generating a 64-char hash that would break delivery without a word; `hasFudpId` is the guard against exactly that. `tools/vector-gen` now compiles the real FC-AJDK `ImMessage` and emits 14 message vectors plus the enum ordinal tables. 19 tests.

> **▶ Phase 9.1.3 (2026-08-14).** Carve *with* a recipient output, and the notice-fee policy — the one place Mail needs new wallet machinery. Until now `selectForCarve` built an OP_RETURN with no payee and `select` built a payee with no OP_RETURN; a mail needs both plus change, because **a mail is addressed by paying its recipient** — the FEIP carries no `to`, so the transaction's pay output is the only record of who the mail was for. `CoinSelector.selectForCarve` gained `payAmount` (the payment is funded *and* sized in both the with-change and no-change shapes; when the leftover is dust the recipient is still paid in full and only the sender's remainder burns), `TxBuilder.buildUnsignedCarve` gained `toFid`/`payAmount` emitting **pay → change → OP_RETURN** per `TxHandler.createTx`, and `WalletService.carve` gained `payTo`/`payAmount` with a guard that a half-specified payment can't quietly degrade into a mail nobody receives. **`NoticeFee`** is satoshis end to end, converting exactly once at the chain boundary — `Freer.noticeFee` is a coin-denominated string, and Android carries *that* as a coins-double while carrying the fee a received mail paid as a satoshi-Long, then compares and assigns between them, so a reply pays 10 000 **F** instead of 0.0001 (Android issue **C9**, high). The parser is strict by grammar because `Decimal(string:)` succeeds on a prefix: `"1,5"` would otherwise parse as **1**, a third of what a European-formatted record meant to charge. Two deliberate divergences: the max-paying cap is applied *after* the pay-back bump (Android applies it before, so a correspondent can step around your limit by attaching a large fee to their mail), and a published fee of zero still pays dust, since with no output the mail has no address at all. **`MailFeip.maxBodyBytes`** — 2 786 — is measured by binary search against a synthetic envelope of exactly the encoder's shape, so it can't drift from reality; Android checks the *plaintext body* against the 4 096-byte OP_RETURN limit and so lets you write 4 000 characters that fail at broadcast, after the mail is encrypted, the fee decided and the tx signed (Android issue **C10**). `ActiveSession` gained the `quoteMail` → `sendMailOnChain` pair: the quote answers "can I mail them at all" (an FID that never spent has no published pubkey, so there is nothing to encrypt to) and "what will it cost" *before* the user writes anything, and `sendMailOnChain` takes the quote rather than a raw amount so a fee the user declined has no satoshi value a forgetful caller could spend. 40 tests, including a decode of the broadcast raw hex proving the pay output exists, pays exactly the fee, and precedes the change and the OP_RETURN — and that the recipient's own key opens what was broadcast.

> **▶ Phase 9.1.1 (2026-08-14).** `AsyTwoWayCipher` — the envelope every mail rides in, and the first piece of Mail-before-IM. Contacts and Secrets seal to *yourself*, so ``AsyOneWayCipher`` was enough: an ephemeral sender key, `pubkeyA` recorded, its private half thrown away. A mail has **two** readers, so `Encryptor.encryptByAsyTwoWay` does the ECDH with the sender's *real* key and records **both** `pubkeyA` (sender) and `pubkeyB` (recipient); either party pairs their private key with whichever pubkey isn't theirs. Without that, a sent mail is write-only and an outbox is impossible — which is the one test (`testSenderOpensTheirOwnMail`) worth pointing at. Ported Java's side-selection from `Decryptor.decryptTry`, added the encrypt direction (GCM, fresh 12 B iv, HKDF-SHA512 salt=iv info="hkdf", field order = Gson declaration order), and an `AsyCipher` dispatcher that routes by the envelope's own `type` — a mailbox holds AsyTwoWay correspondence *and* AsyOneWay notes-to-self, and which is which belongs to the record, not the call site. **Both algorithms had to be readable**: Android's carve path (`Mail.encryptContent`) uses **CBC** while its local-save path uses GCM, so a GCM-only port would have failed on every mail ever put on chain (logged as Android issue C7). CBC has no AEAD tag, so `verifySum` now implements Java's `makeSum4` — `sha256(symkey ‖ iv ‖ sha256x2(plaintext))[0..<4]` — and the CBC tamper test proves it is load-bearing: 8 corrupted-byte positions, every one rejected, where without the sum some would have decrypted to garbage and rendered as a mail body. Skipped for the legacy P7 alg, whose sum is computed over the ciphertext instead. Vectors come from the **real FC-AJDK `Encryptor`**, round-tripped through its own `Decryptor` at generation time (`AsyTwoWayRef.java`, 10 vectors × 2 algs × ascii/unicode/1-char/4 KB + the two self-addressed AsyOneWay cases); regeneration left every pre-existing vector byte-identical. The zero-length payload is deliberately not a vector — FC-AJDK's decryptor rejects what its own encryptor produces for empty input (Android issue C8). 13 tests.

# FreerForMac — Migration Plan

A fresh-start Swift/SwiftUI rewrite of the Android Freer cryptographic wallet + IM/mail suite. Target is a clean, idiomatic macOS-native app — not a line-by-line port.

## Decisions locked (2026-04-24)

| # | Decision |
|---|---|
| 1 | **Transport:** FUDP + FAPI only. **APIP is retired** and will not be ported. |
| 2 | **Blockchain parity target:** `freecashj`, which is a fork of bitcoinj (BitcoinCash branch, ~2019-11-15). Tx/Script serialization must be byte-identical to that fork. |
| 3 | **KDF:** Argon2id, `iterations = 3`, `memory = 65536 KiB (64 MiB)`, `parallelism = 1`, `derivedKeyLen = 32`. |
| 4 | **Mnemonic dropped.** No BIP39 on Mac (or Android going forward). Passphrase → Argon2id → 32-byte private key. |
| 5 | **Target:** macOS 14 Sonoma (`@Observable`, Swift 5.9+). |
| 6 | **Bundle ID:** `fc.freer.mac`. |
| 7 | **Signing:** Developer ID available; sign + notarize for distribution. |
| 8 | **Scope:** full feature parity with Android (wallet, keys, secret, multisig, tx, tools, qr, contact, im, mail). |
| 9 | **Phase ordering:** wallet first, IM second. |
| 10 | Android bugs are tracked in `<android-repo>/docs/android-issues-to-fix.md`; append as we find more. |

## Design principles

- **SwiftUI-first**, AppKit only for windowing/menus SwiftUI cannot express cleanly.
- **Swift Concurrency** (`async`/`await`, actors). No callbacks or `DispatchQueue.main.async` scattered in view models.
- **`@Observable` MVVM.** No app-wide singletons. The Android "Manager" pattern becomes per-identity scoped dependency containers, passed explicitly.
- **Per-identity isolation at the type level.** An `Identity` value owns its own storage handle, FUDP session, and services — the compiler prevents mixing identities' data.
- **`Codable` everywhere.** One JSON path. No Gson/Jackson dualism.
- **Zeroize secrets.** Passwords live in `Data` (or `UnsafeMutableBufferPointer<UInt8>`) and are explicitly zeroed after use. Never `String`.
- **No premature abstraction.** One concrete implementation per service until a second call site appears.

### Phase 1 — `FCCore` crypto foundation · ✅ complete

All primitives are live in Swift and cross-verified byte-for-byte against Java-generated vectors produced by `tools/vector-gen/` (freecashj v0.16 + BouncyCastle). Commits 7738391 → 260843f.

| Primitive | Scheme | Parity |
|---|---|---|
| Hashes | SHA-256, double-SHA-256, RIPEMD-160, Hash-160 | byte-exact |
| KDF (password) | Argon2id (iter=3, mem=64 MiB, par=1, 32 B) | byte-exact |
| KDF (key) | HKDF-SHA256, HKDF-SHA512 | byte-exact |
| AEAD | AES-256-GCM, ChaCha20-Poly1305 | byte-exact |
| secp256k1 | pubkey derivation, ECDSA sign / verify, ECDH | byte-exact for ECDH + verify; ECDSA sign round-trips (libsecp256k1 and BouncyCastle disagree on RFC 6979 internals — either side verifies the other) |

- **CashAddr** — FCH does not use CashAddr. FCH addresses are Base58Check only.

**Golden tests are non-negotiable.** We feed the same inputs as Android and byte-compare outputs. No parity → no build.

- Per-identity isolation enforced at the type level: every domain service takes an `Identity` and pulls its `EncryptedKVStore` from there. No global "current identity" singleton.
- Use cases = `async` functions returning typed results (`throws` rather than `Result<T,E>` — Swift's typed-throws still requires opt-in and Result fights `try`).
- Each store namespaces its keys (`settings:*`, `keys:*`, `contacts:*`) inside the shared per-identity `EncryptedKVStore` — one DB per identity, not one per concern.

**Cache architecture (Three Patterns).** FCH's `lastHeight` is on every chain entity — every cache becomes incremental.

| Pattern | Shape | Sync | Used for |
|---|---|---|---|
| **A** | Watermark-synced collection by `lastHeight` | Bootstrap once, then `lastHeight > localMax − 30` (reorg window) | `CashesStore` (the wallet's spendable cash set) |
| **B** | Cipher-always-stored + plaintext decryption overlay | Cipher rows persist; plaintext lives only in memory under the symkey | Reserved for future per-main encrypted artifacts |
| **C** | Cursor-paginated stream blob | Append on next-cursor, replace on filter change | `RecentActivityStore` (Transactions pane, key per-kind: all / incomes / expenses) |

**Wire / consensus gotchas worth not relearning:**
- **P2PKH spends require BCH-Schnorr.** ECDSA-DER is rejected by mainnet with the misleading error `Signature cannot be 65 bytes in CHECKMULTISIG`.
- **FCDSL `query` vs `filter`.** Both are separate fields on the POJO. `base.search` consumes `query` via `queryExecutor.executeQuery`; `base.cashValid` mode-1 reaches for `filter`. Mixing them up causes silent timeouts.
- **FUDP STREAM frames must be reassembled.** Responses ≥ ~1 KB span multiple STREAM frames sharing a `streamId`, with `offset` and `fin` only on the last. Decoding each as a complete AppMessage corrupts the receiver's state and breaks every call after the big one.
- **Bootstrap fallback:** `base.cashValid` mode-2 (`params: {fid}`) is the known-working bootstrap. Incremental `base.search` is fail-soft — on any error it falls back to mode-2.

**UX rules locked in (saved as feedback memory):**
- Every FID and every toast/error is click-to-copy with a green-checkmark flash (`CopyableText` in FCUI).
- Every truncated ID renders middle-elided: `head + "…" + tail`, never `prefix(N)`. Use `String.elidingMiddle` or `CopyableText.elidingMiddle`.

### Phase 8.4 — HAT + file management · ~5d · **Phase 9 prerequisite**

Port of Android's `HatManager` + `DataSyncManager` + `DataActivity`/`HatFileOpener`. A `Hat` is a **local-only** (no blockchain sync, no FEIP) file-metadata record: `id` = DID = hex `sha256x2(content)`, `locas` = list of locations (`local://<path>`, `fudp://host:port`, `(sid)<serviceId>`), plus the two-HAT cipher fields. IM file messages (Android `FileShareHelper`) serialize the **raw HAT JSON as the message content** with the plaintext `key` and DISK locas copied in — the receiver adds that HAT to its own store and downloads via the plain-key path. So this layer, wire-compatible with Android's `Hat.toJson()`, must exist before Phase 9.

**Two-HAT cipher model (`DataSyncManager` parity).** Upload: random 32 B symkey → encrypt file → cipher DID = sha256x2(cipher file) → `kCipher` = AsyOneWay-encrypt the symkey to the owner's own pubkey (same envelope as 7.6.3's `AsyOneWayCipher`) → `disk.put` (temp, `dataLifeDays`) or `disk.carve` (permanent) → create cipher HAT (`id=cipherDid, rawDid=rawHat.id, kCipher, size, locas=[(sid)… preferred, fudp://… fallback]`) → append cipherDid to raw HAT's `cipherIds`. Download: (1) raw HAT's remote locas direct — **hash-verify against the DID, servers are untrusted**; (2) per cipherId: plain-key path first (`rawHat.key`, works without the cipher HAT in the local DB — the IM receive path), then kCipher path (decrypt with live privkey); stream-decrypt; plaintext must hash back to the raw DID; write into the app data dir and add a `local://` loca. Accumulate per-attempt failure diagnostics into the surfaced error (Android's `diag` string — keep it, it's what makes DISK failures debuggable).

**The Mac difference — reference, don't copy (decision 2026-08-13).** Android copies every imported file into `filesDir/data/<did>` because SAF content URIs aren't stable. On macOS (unsandboxed SwiftPM build) we register the **original file's path** as the `local://` loca — no copy, no doubled disk usage, instant import even for GB files. Reference-mode guard: a `HatLocal` sidecar (persisted next to the wire `Hat` in the store row, **never** serialized into IM/export JSON) records size+mtime per referenced path at registration; every access `stat`s the file — missing → drop the loca (self-heal); size/mtime changed → re-hash; hash ≠ DID (edited in place) → detach the loca and offer re-register-as-new-version (`preDid`/`srcDid` links). Cost: one `stat` per access; re-hash only on actual change. Downloads and explicit "materialize a copy" land in `Application Support/FreerForMac/<mainFid>/data/<did>` (checked as an implicit loca, like Android's `filesDir/data/<did>` fallback). A received HAT's foreign `local://` paths simply fail the `stat` and are ignored. If the app is ever sandboxed for distribution, `HatLocal` grows security-scoped bookmark data — field reserved now.

### Phase 8.8 — Publish · ~3.2d · ✅ complete

The six FEIPs in the **Publish** category — Statement (8), Text (21), Remark (22), Sound (23), Image (24), Video (25) — are what a FID puts out for everyone to read, as against what it registers (Construct) or sends to one person (Personal). So this is the first feature in the plan built from the protocol spec and the server-side parser alone, which is why the four decisions below are written down here rather than inherited from a working client.

**1. The body is not on the chain, and `did` is what it hashes to.** FEIP21 has no content field: a text record is `title` + optional `summary` + a `did` pointer, and the work itself lives wherever `did` says. `did` is opaque to the indexer — a keyword, never dereferenced — so a convention had to be chosen, and the choice is the one the rest of this app already uses: **`did` is the raw DID, hex `sha256x2` of the body, and the bytes go to DISK through the Phase 8.4 stack** (`FileVault.registerFile` → `HatSyncService.uploadRaw`, a permanent `disk.carve` rather than an expiring `put`). That makes the pointer self-verifying — a reader hashes what it fetched and compares against the carve, so a DISK serving the wrong bytes is caught rather than believed — and it costs nothing new: the upload, the hash-on-arrival check and the local cache are all machinery 8.4 already shipped for file transfer. **Every publish uploads**, including a two-line note; `summary` is the on-chain preview a list draws without fetching anything, not a place to smuggle the body.

Reading somebody else's work is three attempts in order: the local HAT store (we published it, or read it once already), our own DISK, then the publisher's home DISK resolved through `HomeServiceResolver` — the same `(sid)` bootstrap the message path uses to find a stranger's DOCK. A body that none of the three can produce leaves the record readable and the reader honest about why.

**2. `onDid` is the target's record id.** A remark can anchor to its target's `did` (the spec's wording) or to the target's publish txid; both are 64 hex characters and the field is one keyword, so the two id spaces coexist without ambiguity but a client has to pick one and stay picked. **It is the txid**: every UI already holds it, a record may legally be published with no `did` at all, and it makes the anchor uniform across all five things one can remark on — including another remark, which is what makes a thread.

**3. `rate` is built, not wired** — exactly where 8.7.5 left it for the Construct four. The op builders and the `tRate` / `tCdd` display ship here; the action waits for weight-aware coin selection, since a rating's weight is the coin-days its transaction destroys and 7.9's `CoinSelector.fixed` is what will supply them. The floor is only 1 CD (`CddRequired = 1`), which the carve path already guarantees, so what is deferred is *control over the weight*, not the ability to rate.

**4. Three server-side defects, fixed in `FEIP/FeipParser` as part of 8.8.1.** They are in the reference parser rather than the client, and the first one means the protocol does not currently work:

- **`Text` publish never sets `ver`.** `makeText` does not copy `ver` into `TextHistory`, and `parseText` then assigns that null onto the entity. Every published text row carries `ver: null`, and `update` — which does `Integer.parseInt(text.getVer()) + 1` inside a method declared `throws Exception` — raises `NumberFormatException` on the first attempt. **Text update is broken on the server today.** `parseRemark`, `parseSound`, `parseImage` and `parseVideo` all hardcode `setVer("1")` at the same point; `parseText` is the only one of the five that does not, which is what makes this a typo rather than a design.
- **The FEIP6 master bypass is inverted**, identically in `parseText` and `parseRemark`: on `delete` / `recover` by a non-publisher it loads the **signer's** `Freer` and requires `signer.master == signer`. It should load the **publisher's** and require `publisher.master == signer`. As written a master can never delete anything, and the bypass the spec documents is dead code.
- **`update` clears omitted fields.** The reference copies every metadata field from the history onto the entity including nulls, so an update that mentions only `title` wipes `summary`, `lang`, `authors`, `format` and `did`. The spec records this as intended; the client therefore **resends the record's whole mutable half on every update**, the way the Construct four already do, and `testAnUpdateResendsEveryFieldRatherThanClearingThem` pins it on the decoded transaction.

**What the client tolerates regardless.** `ver` is optional on the way in and rendered as "—" when absent, because rows published before the fix will carry null forever and a reader that trusted the field would show nothing at all.

### Phase 9 — Mail + IM · 10d · **largest feature chunk**

**Ordering: Mail first (9.1), IM second (9.2)** — reversed from the original outline on 2026-08-14. Mail is a *carve-and-sync* feature with exactly the shape we have now shipped twice: an on-chain FEIP entity whose payload is an encrypted `CryptoDataStr` envelope, paged out of `base.search`, decrypted locally, merged into a per-main store — Contacts (7.6.2b/7.6.3) and Secrets (8.2) are the same program. IM is a *live-session* feature: rooms/squares/teams, an inbound FUDP push path, per-session key agreement, message adapters. Android's `mail/` is 4.7 k lines against `im/`'s 26 k. Doing Mail first reuses machinery that is already load-bearing, keeps the phase's first deliverable close, and — the real reason — the two prerequisites Mail forces out (AsyTwoWay envelopes, carve-with-a-recipient-output) are both things IM needs anyway.

#### Phase 9.1 — Mail · ~4d · ✅ complete (2026-08-14), pending the live acceptance run

Port of Android's `mail/` (`MailActivity` / `CreateMailActivity` / `ReadMailActivity` / `DeleteMailActivity` / `MailDeletedActivity` / `SetNoticeFeeActivity`) + `manager/MailManager`. So unlike a contact or secret carve, the sender's FID and the recipient's FID are public; only the body is sealed.

### Phase 11 — 中文 / Localization · ~7d

The app has never been localized and this document has never said so. Decision 8 promises "full feature parity with Android", and Android has shipped `values-zh/` since the beginning — so a Mac build that speaks only English is a parity gap that no phase owns. The two places localization *is* mentioned here are both prohibitions (9.2.6's confirm sentences must not be reworded or localised; 8.4.3's HAT DID hashes the bytes), which is the shape of the whole phase: **localization stops at the view layer, and the interesting work is defending that line.**

**The glossary already exists and is not ours to invent.** `<android-repo>/app/src/main/res/values-zh/strings.xml` holds **2,160 translated strings** in the product's own voice — 飞人, 明人 for Nobody, 名单 for a FID list, 秘密, HAT详情. Terminology is *extracted* from that file rather than translated afresh, because the failure mode is not a clumsy sentence but two apps calling the same thing two different names to a user who runs both. Where the Mac has no Android counterpart — reference-mode file handling (8.4), the service picker, the four-tab chat split (9.2.8) — new terms get written here and proposed back to Android's file, so the drift stays one-directional and there is one dictionary rather than two.

**Protocol strings are not text.** The FEIP confirm sentences a member signs, the multi-word ops that carry a space (`take over`, `agree consensus`), `sn`/`ver`, JSON field names, Gson's escaping tables, and the `Locale(identifier: "en_US_POSIX")` in `NoticeFee.swift:115` are all wire format that happens to be spelled in letters. A locale-aware `Decimal(string:)` is an interop bug that reads like a typo. So `FCCore`, `FCTransport` and `FCDomain` get **no string catalog at all** — only `Sources/FreerForMac` and `FCUI` do — and that is a rule a build can check rather than a rule to remember.

**The error path is the actual cost, not the labels.** Domain code hands English to the UI through `NSLocalizedDescriptionKey: "non-utf8 JSON output"` and the views print it raw (`AddMainView.swift:142` is `String(describing: error)`). Translating that means typed error enums in the domain with the mapping to human text done in the view — a real refactor, and most of this phase. The `Text("…")` sweep is volume by comparison. One deliberate exception: 8.4's accumulated per-attempt DISK `diag` string **stays English**, because it exists to be pasted into a bug report and a translated stack of failure causes helps nobody who can act on it.

**SwiftPM means doing the plumbing by hand.** `defaultLocalization: "en"` on each package with UI, `en.lproj/Localizable.strings` + `zh-Hans.lproj/…` under a `.process`-ed `Resources/`. The trap is that `String(localized:)` resolves against `Bundle.main`, and a SwiftPM executable's resources land in a *generated* bundle beside the binary — so every lookup needs `bundle: .module`, and `FCUI` needs its own catalog and its own bundle. Phase 10's real `.app` is where `Bundle.main` starts working, which is exactly why the lookup goes through one helper now: the packaging phase then changes one line instead of 1,600 call sites. Same reasoning as 9.2.7c's `Info.plist` — do the small thing that survives the bundle arriving later.

**The bugs are not in the words.** Four that no amount of translation fixes:

- **`MessageComposerView.swift:156-160` is a `TextField` with `.onSubmit(onSend)`.** Under a Pinyin IME, Return confirms a candidate — as written, the first Chinese message anyone types gets sent half-composed. The composer needs to ignore Return while marked text exists. This is the most user-visible defect in the app for a Chinese user and it is present today.
- **`ContactsStore.swift:83` sorts with `localizedCaseInsensitiveCompare`**, which orders Chinese names by code point. A contact list that looks randomly shuffled reads as a broken app, not a sorting preference; it needs `localizedStandardCompare` or an explicit pinyin collation.
- **`FidSearchModel` matches substrings only.** A Chinese user types pinyin initials to find 张三 and gets nothing.
- **Layout.** Fixed `.frame(width:)` labels and `lineLimit` truncation behave differently where there are no word boundaries — an audit, not a find-and-replace.

FIDs, CIDs and hashes stay Latin monospace and keep the middle-elision rule (head + … + tail) in every language.

**Language selection follows the system, with an explicit override.** Default is the system locale; Settings gets a picker anyway, because this product's users routinely run an English system deliberately — and the reverse. A root-level `\.locale` plus an explicit bundle handle the in-app switch.

**Ordering: after 9.2 closes.** Extracting strings from views that are still being written means doing it twice — `RoomSettingsSheet`, `FidPicker` and `ServicePicker` are all untracked as of today. What lands *now* is the plumbing decision (11.2), so that no view written from here on adds a raw literal.

## Key risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | **FUDP parity.** Custom protocol; any byte-level drift breaks interop with existing servers. | Interop harness against a live Android-spun server as early acceptance test (end of Phase 4). |
| R2 | **Tx serialization parity** with freecashj (BCH 2019-11-15 fork). Sighash quirks, BIP143-style preimage details. | Parity harness with captured tx hex fixtures (end of Phase 2). Do not advance to Phase 3 until it is green. |
| R3 | **Schnorr compatibility.** freecashj's Schnorr may predate BIP340 finalization and use non-standard R/tags. | Inspect freecashj source, mirror exactly. Add vectors from a freecashj-signed fixture set. |
| R4 | **macOS sandbox entitlements** — Keychain, camera (QR), microphone (voice msg), network-client, file-access for downloads. | List entitlements up front in Phase 0; add `.entitlements` file; test each in its feature's phase. |
| R5 | **Argon2 Swift library maturity.** Pure-Swift Argon2 implementations are rare. | Use `CatCrypto` (wraps reference C impl) or bundle `argon2` as a SwiftPM system target. Bench on target hardware. |
| R6 | **Single-engineer scope.** ~51 days is long; priorities may shift mid-flight. | Each phase produces a runnable artifact; pause-points are natural if scope trimming is needed. |
| R7 | **A translated string reaching the wire** (Phase 11). FEIP confirm sentences, multi-word ops and HAT DID bytes are text that must never be localised; a well-meaning sweep breaks interop silently and only on the Chinese build. | No catalog in `FCCore`/`FCTransport`/`FCDomain` at all, enforced by the 11.2 build check; the existing byte-parity vectors fail loudly if one gets through. |
