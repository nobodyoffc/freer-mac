> **▶ Phase 9.2.3 (2026-08-14).** The keys group traffic is sealed with. **Every version is kept forever** — a rotation *adds* a key rather than replacing one, because messages already sealed under v3 still have to open after the room moves to v4 and this store holds the only copy of v3. So "the room's key" always means the newest version, while decryption always asks for the version the message names, and `SymkeyStore.open` reaches for that one rather than the current one. **A received key never overwrites one we hold** unless the caller vouches that the sender is the entity's owner: without that rule any member could push a bogus key for an existing version and make everyone's history unreadable. The store cannot know who the owner is — that lives with `Room`/`Team` in 9.2.5/9.2.6 — so it takes the answer as an argument and makes the caller state it, and refusing an overwrite is an ordinary `false`, not an error, since two members answering the same request is the normal case. Non-positive versions are refused, and that guard is real rather than decorative: `symkeyVersion` is a 64-bit field the wire carries in **32** bits and sign-extends coming back (9.2.1), so a peer genuinely can name a negative version, and storing a key there would put it where no honest rotation could reach. **We store the key itself; Android stores it sealed** — Android wraps each key AsyOneWay under the user's own pubkey because on that platform the row has only the app sandbox behind it, while here the row is already AES-GCM under a vault key that is `HKDF(configure symkey, …)`, derived from the very password that releases the identity privkey. Same gate twice buys nothing and would cost an ECDH per message decrypted; not having it is why this store needs no in-memory key cache and Android's does. Storage keys pad the version to 19 digits so `listKeys` answers `versions`/`currentVersion` without decrypting anything (v10 must not sort before v9), and parse on the *last* underscore so an entity id containing one survives. `ImMessageBody` gives the model the same seal/open pair `Mail` has, with the same asymmetry — sealing throws, because the alternative is plaintext on the wire; opening returns false, because a batch arriving after a rotation will contain rows we cannot read yet and each is a key to go and ask for, not an error to abort on. P2P bodies reuse 9.1.1's AsyTwoWay so the sender can reread their own messages, with the note-to-self AsyOneWay exception `Mail` already needed. The SYMKEY payload is `entityId:cipher`, split on the **first** colon always — the cipher is JSON and is full of colons of its own. 25 tests.

> **▶ Phase 9.2.2 (2026-08-14).** Where messages live. Chat history is **the first collection in this app with no ceiling** — every other store is human-scale and can answer `all()`, which is exactly what `TypedStore`'s own doc comment warns against here — so `MessagesStore` is shaped around never loading what it is not showing: **one `EncryptedKVStore` namespace per conversation** (`im.messages.v1.<threadId>`, so opening one chat never touches another's rows) and a key of **zero-padded timestamp + message id**, which makes SQLite's `ORDER BY key` the transcript's own order and paging a slice of a string array — no ciphertext is decrypted until a row is actually wanted. 19 digits is `Int64.max`, so every timestamp pads to the same width and text order is numeric order; a negative timestamp clamps rather than wrapping into a shorter string that would sort in the wrong place. `page(before:limit:)` walks backwards the way a chat view scrolls, and a nil `olderCursor` doubles as "no more". The cost of the shape is that find-by-id is a scan of that conversation's *keys* (never its values) — bounded and cheap, but not an index, and the note says when to add one. **Bodies are stored open when they could be opened** — the deliberate opposite of `MailsStore`: a mail's cipher can always be reopened with the identity key, while an IM cipher is an ephemeral transport wrapper whose symkey version may be rotated away, so keeping it would mean holding a blob that goes unreadable while the plaintext beside it stays fine; the cipher is kept only for a message we could *not* open, where it is the sole copy. The store also refuses to name a message (`put` throws without an id) because ids belong to the FUDP layer, and `mutate` re-puts under the *original* key so a status change cannot move a message in the transcript. `ConversationsStore` is the index over it, human-scale and explicitly **a cache**: `rebuild(id:from:)` recovers every field from the messages, which is what makes optimistic updates on the delivery path safe. Two judgment calls beyond the port: an older message arriving late (DOCK backlog after a direct send) counts as unread and moves the thread's birthday back but does **not** rewrite the preview, and `ContentType.isDisplayable` keeps signals out of the unread count — otherwise a peer could hold a conversation at the top of the list by typing at it forever. New in FCStorage: `listNamespaces()`, since namespaces stopped being compile-time constants. 34 tests.

> **▶ Phase 9.2.1 (2026-08-14) — opens Phase 9.2 (IM).** `ImMessage` and the five enums it routes on. The phase breakdown is new too: 9.2 was five bullets and is now seven sub-phases, ordered bottom-up (message → store → key → delivery → groups → pane) so each layer is testable without the one above it. **An IM message has two serializations and they disagree on purpose.** `wireJson()` is the local-storage form and carries everything, including this device's delivery bookkeeping; it also crosses devices, because a HISTORY share writes one line of it per message into a file the other client reads back — so Gson's rules bind here exactly as they do for `Mail`: declaration order, nulls omitted, HTML escaping off, enums **by name**. `toWireBytes()` is what actually travels, and it carries only what the recipient could possibly know — no `status`, no `roadIds`, no `dockId`, no `readAt`, no `unread`, no `sequence` — because those describe *our* relationship to the message and a port that preserved them would be handing the receiver invented facts about itself. On the wire the same enums go **by ordinal**, which is the sharp edge of the whole sub-phase: a transposed case keeps every JSON test green while silently re-labelling every message (a `VOICE` arriving as a `ROOM_LEAVE`), so `JavaOrdinalEnum` derives the ordinal from declaration order rather than restating it and the vectors pin all 43 constants by number. Three lossy behaviours are **reproduced, not repaired**: `symkeyVersion` is a Long the wire carries in 32 bits (a version past 2³¹ arrives sign-extended and negative), a nil `type`/`contentType` writes ordinal 0 and so arrives as `P2P`/`TEXT`, and empty-vs-nil is indistinguishable for the length-prefixed strings. Widening any of them would just be a different protocol. Unlike `Mail` and `Hat`, **the id is not derived** — it is the FUDP layer's 64-bit message id in 16 hex chars, over the *bit pattern* (half of all ids are negative), and Java's `getId()` override exists solely to stop `FcEntity` auto-generating a 64-char hash that would break delivery without a word; `hasFudpId` is the guard against exactly that. `tools/vector-gen` now compiles the real FC-AJDK `ImMessage` and emits 14 message vectors plus the enum ordinal tables. 19 tests.

> **▶ Phase 9.1.6 (2026-08-14) — closes Phase 9.1.** The notice-fee setter (`SetNoticeFeeActivity`). **`NoticeFeeFeip`** is sn 10 ver 1, and it is the one place a fee leaves satoshis: the value goes on the wire as a **coin-denominated string**, because that is how it lands on `Freer.noticeFee` and how every sender's client reads it back — which is exactly what `NoticeFee.coinString(satoshis:)` exists for. The protocol has no `op` and no delete: republishing overwrites, and `"0"` is how you stop charging (a real statement, distinct from having published nothing, which makes senders pay the default). Two guards that are ours rather than the protocol's: a fee is refused above **`maxPublishableSats`** (1 000 F) and below zero, because a published rate can only be changed by *another* carve, so a single typo'd zero would leave the FID unreachable and the fix would itself cost a transaction. `ActiveSession.carveNoticeFeeOnChain` uses the paymentless carve — publishing a rate is a statement about us, not a message — and `publishedNoticeFee()` reads the current rate back **from the chain** rather than from a local copy, since the carve may have been made on another device and a stale local number would misreport what senders are actually being charged. **Settings** gains a Mail section: My notice fee (with its own Carve button, the on-chain value in the hint, and the button disabled when the chain already says that), Most I'll pay, and the pay-back toggle — the last two are local preferences riding the existing Save button, and the footer states plainly which of the three leaves the device. This is the destination the compose sheet's "Raise the limit in Settings" was already pointing at. 10 tests, incl. the round trip that matters — what we publish is what a sender's `decide` reads back — and proof that a rate carve pays nobody. **Phase 9.1 (Mail) is complete**; the live cross-platform acceptance run is the remaining gate before 9.2 (IM).

> **▶ Phase 9.1.5 (2026-08-14).** `MailView` — the pane (`MailActivity` + `ReadMailActivity` + `DeleteMailActivity` + `MailDeletedActivity`). Three tabs over one store (Inbox / Sent / Deleted), unread count in the tab label, search that runs over rows **with their decrypted bodies attached** so a query matches text the reader can actually see, `Load more` pagination, and per-row reply/delete. **Bodies are sealed at rest, so the pane decrypts only the rows it is about to draw**, once each per pane life — which is why the list paginates at all: every row costs an ECDH the first time it appears, and rendering a whole mailbox would spend thousands up front. Plaintext lives in a `[String: String]` in the view and is never written back. **The envelope is public and the UI says so out loud**: a "Public on the chain" block in the read sheet lists both FIDs, the time, the fee and the txid under a plain statement that only the message above was encrypted — padlocks otherwise imply more privacy than a mail has. `MailComposeSheet` is built around the fact that **sending costs money and can be refused**, so the quote comes first: as soon as the FID parses we look it up and answer the two questions the user cannot guess — no published pubkey means no mail is possible *at all* (nothing to encrypt to), and a fee over their limit means it will not be sent — where Android asks both only after the message is written and Send is pressed. A live byte counter runs against `MailFeip.maxBodyBytes` rather than the 4 KB OP_RETURN limit, so the overflow is visible while typing instead of at broadcast, and the confirm alert states the fee, the payee and that the two FIDs and the time cannot be taken back. Delete offers **Delete on-chain** (a carve, recoverable) beside **Remove from this device**, with the alert saying plainly that the local-only option is undone by the next sync — the same trap the Contacts pane has. The carve flips the local row immediately so the mail changes tab now rather than at the next sync. Reply ports `makeReplyHead` verbatim so a reply written here reads the same in the Android client. **Verified, not assumed**: the sidebar was checked with the five-line `WalletPane` driver from the 8.4.6 lesson — 10 of 10 cases rendered, no unreachable panes — and the app was launched to confirm it starts clean. The pane itself has not been driven at runtime (it is behind the vault password), so its first real exercise is the live acceptance run.

> **▶ Phase 9.1.4 (2026-08-14).** `MailService` — the read path (`MailManager.refreshMailsFromAPI` → `makeEntityDetails`). **One query covers both directions**: a mail's `from` and `to` are public index fields, so `equals` over *both* against our own FID returns the inbox and the outbox together — contacts and secrets are carved to yourself and only ever have an `owner`. No `active` filter, because a delete carved on another device only reaches this one as an `active:false` row. Records decode straight into ``Mail`` — it is already the wire shape, so there is no parallel `OnChainMailRecord` to keep in step. **Three deliberate divergences from the contact and secret syncs, each because mail is addressed rather than self-carved:** (1) an **undecryptable row is kept and flagged**, not skipped — a contact whose cipher won't open is unusable because the FID is *inside* the ciphertext, but a mail's correspondent is on the outside, so the row still truthfully says who wrote and when, and dropping it would quietly hide mail; (2) a **deleted row is kept**, not removed, since the chain can recover it and Recover would have nothing to act on otherwise (`MailsStore.deleted()` is the Deleted view); (3) **only incoming mail arrives unread** — Android's `markEntityAsNew` marks everything, which leaves your own outbox lit up after a fresh sync — and read state is local, so a re-sync never relights a mail you have opened. Decryption during sync is a *trial run* whose plaintext the store drops: all that is kept is the `decrypted` flag, so a list can tell "not opened yet" from "needs a key this identity doesn't have". Rows already known to open are not retried (an ECDH per mail per sync for an answer we hold), but rows that *failed* are, since the last sync may have run watch-only — which also forced a fix in `MailsStore.upsert`, where 9.1.2 had been clearing the flag along with the plaintext; the flag is a fact about key availability, not about content, and persisting it is what makes the distinction survive a launch. Incremental sync exits the page walk once a page drops below `watermark − 30` (height-descending order makes that safe, and the 30-block reorg window matches the cash cache), with `contacts` optionally caching correspondents' CIDs — not their FIDs, which the row already carries. 19 tests, incl. real AsyTwoWay round trips in both directions, the reorg-window boundary in both directions, and a remote delete flipping an existing row.

> **▶ Phase 9.1.3 (2026-08-14).** Carve *with* a recipient output, and the notice-fee policy — the one place Mail needs new wallet machinery. Until now `selectForCarve` built an OP_RETURN with no payee and `select` built a payee with no OP_RETURN; a mail needs both plus change, because **a mail is addressed by paying its recipient** — the FEIP carries no `to`, so the transaction's pay output is the only record of who the mail was for. `CoinSelector.selectForCarve` gained `payAmount` (the payment is funded *and* sized in both the with-change and no-change shapes; when the leftover is dust the recipient is still paid in full and only the sender's remainder burns), `TxBuilder.buildUnsignedCarve` gained `toFid`/`payAmount` emitting **pay → change → OP_RETURN** per `TxHandler.createTx`, and `WalletService.carve` gained `payTo`/`payAmount` with a guard that a half-specified payment can't quietly degrade into a mail nobody receives. **`NoticeFee`** is satoshis end to end, converting exactly once at the chain boundary — `Freer.noticeFee` is a coin-denominated string, and Android carries *that* as a coins-double while carrying the fee a received mail paid as a satoshi-Long, then compares and assigns between them, so a reply pays 10 000 **F** instead of 0.0001 (Android issue **C9**, high). The parser is strict by grammar because `Decimal(string:)` succeeds on a prefix: `"1,5"` would otherwise parse as **1**, a third of what a European-formatted record meant to charge. Two deliberate divergences: the max-paying cap is applied *after* the pay-back bump (Android applies it before, so a correspondent can step around your limit by attaching a large fee to their mail), and a published fee of zero still pays dust, since with no output the mail has no address at all. **`MailFeip.maxBodyBytes`** — 2 786 — is measured by binary search against a synthetic envelope of exactly the encoder's shape, so it can't drift from reality; Android checks the *plaintext body* against the 4 096-byte OP_RETURN limit and so lets you write 4 000 characters that fail at broadcast, after the mail is encrypted, the fee decided and the tx signed (Android issue **C10**). `ActiveSession` gained the `quoteMail` → `sendMailOnChain` pair: the quote answers "can I mail them at all" (an FID that never spent has no published pubkey, so there is nothing to encrypt to) and "what will it cost" *before* the user writes anything, and `sendMailOnChain` takes the quote rather than a raw amount so a fee the user declined has no satoshi value a forgetful caller could spend. 40 tests, including a decode of the broadcast raw hex proving the pay output exists, pays exactly the fee, and precedes the change and the OP_RETURN — and that the recipient's own key opens what was broadcast.

> **▶ Phase 9.1.2 (2026-08-14).** `Mail` + `MailsStore` + `MailFeip` — the mailbox's data layer. **`Mail`** mirrors `feipData/Mail.java` field for field (alg · cipher · from · to · birthTime · birthHeight · lastHeight · active · content · onChain · decrypted · fromName · toName · unread · noticeFee → `objName` → `id`, Gson's declaring-class-first order). Unlike `Hat` there is **one** encoder, not two: `Mail.toBytes()` is `JsonUtils.toJson`, HTML escaping *disabled*, so a body containing `< > & ' =` is stored and hashed identically — the `local-draft-html-escapable` vector exists to catch a port that reached for Gson's default writer out of habit. `checkIdWithCreate()` hashes **the object as it currently stands**, which is the sharp edge: derive the id before or after stamping `birthTime` and you get two ids for one draft, so `Mail.draft(from:to:content:)` pins Android's `{from,to,content}` shape. On-chain mail never touches that path — its id is the carve txid. `encryptContent` seals AsyTwoWay, or **AsyOneWay when `from == to`** (Java's side-selection can't resolve an envelope whose two pubkeys are equal), and clears the plaintext; `parseDetail` **fails soft**, returning false and marking `decrypted = false` rather than throwing — one unreadable row must not abort a sync, and unlike a contact (whose FID lives *inside* the cipher) an unopenable mail still truthfully names its sender. **`MailsStore`** (`mails.v1`, on `ActiveSession.mails`) keyed by id, sorted `lastHeight desc, id desc` to match `MailManager.makeFcdsl` so a merged page doesn't reshuffle on sync, with Android's `MaX_HEIGHT` (999 999 999) sentinel floating just-sent mail to the top — and `highestKnownHeight` excluding that sentinel, since resuming a sync from it would skip every real mail forever. Deleted mail is **kept**, not dropped: a delete is recoverable on chain, so discarding the row would make Recover blind. The store is the boundary the plaintext cannot cross — `upsert` drops `content` whenever a `cipher` exists, tested directly, while a never-encrypted draft keeps its body because there is nothing to fall back to. **`MailFeip`** is sn 7 ver 4 with send/delete/recover, and its size check is against the **whole carve**, not the body: the envelope plus base64 ciphertext is most of the 4 KB, so a body that looks safely under the limit can still produce a transaction the chain rejects. Vectors from the real FC-AJDK `Mail` class (`MailRef.java`, 7 cases). 32 tests.

> **▶ Phase 9.1.1 (2026-08-14).** `AsyTwoWayCipher` — the envelope every mail rides in, and the first piece of Mail-before-IM. Contacts and Secrets seal to *yourself*, so ``AsyOneWayCipher`` was enough: an ephemeral sender key, `pubkeyA` recorded, its private half thrown away. A mail has **two** readers, so `Encryptor.encryptByAsyTwoWay` does the ECDH with the sender's *real* key and records **both** `pubkeyA` (sender) and `pubkeyB` (recipient); either party pairs their private key with whichever pubkey isn't theirs. Without that, a sent mail is write-only and an outbox is impossible — which is the one test (`testSenderOpensTheirOwnMail`) worth pointing at. Ported Java's side-selection from `Decryptor.decryptTry`, added the encrypt direction (GCM, fresh 12 B iv, HKDF-SHA512 salt=iv info="hkdf", field order = Gson declaration order), and an `AsyCipher` dispatcher that routes by the envelope's own `type` — a mailbox holds AsyTwoWay correspondence *and* AsyOneWay notes-to-self, and which is which belongs to the record, not the call site. **Both algorithms had to be readable**: Android's carve path (`Mail.encryptContent`) uses **CBC** while its local-save path uses GCM, so a GCM-only port would have failed on every mail ever put on chain (logged as Android issue C7). CBC has no AEAD tag, so `verifySum` now implements Java's `makeSum4` — `sha256(symkey ‖ iv ‖ sha256x2(plaintext))[0..<4]` — and the CBC tamper test proves it is load-bearing: 8 corrupted-byte positions, every one rejected, where without the sum some would have decrypted to garbage and rendered as a mail body. Skipped for the legacy P7 alg, whose sum is computed over the ciphertext instead. Vectors come from the **real FC-AJDK `Encryptor`**, round-tripped through its own `Decryptor` at generation time (`AsyTwoWayRef.java`, 10 vectors × 2 algs × ascii/unicode/1-char/4 KB + the two self-addressed AsyOneWay cases); regeneration left every pre-existing vector byte-identical. The zero-length payload is deliberately not a vector — FC-AJDK's decryptor rejects what its own encryptor produces for empty input (Android issue C8). 13 tests.

> **▶ Phase 8.4.6 (2026-08-13).** Files pane — `DataActivity` + `HatFileOpener` ported, closing Phase 8.4. New sidebar pane (`WalletPane.files`) listing raw HATs newest-used first (cipher HATs hidden), live search over the in-memory rows via a new public `Hat.matches(query:)`, and a **status chip per row** naming where the bytes actually are: On this Mac / Local + DISK / On DISK / **File changed** / No copy. That chip is the reference-mode decision surfacing in the UI — it comes from `FileVault.resolve`, which also *heals* the record as it runs, so loading the pane doubles as the self-repair pass that prunes dead paths and detaches edited files. Registration is drag-drop or an open panel, with the panel message saying plainly that files stay where they are. Row actions: open (`NSWorkspace`; remote-only rows download first, as `HatFileOpener` does, rather than making the user fetch then open), reveal in Finder, upload (an alert offering "Store for now" vs "Store permanently" instead of the jargon `put`/`carve`), download, share the record, and a delete alert whose two options — "Remove local copy" vs "Delete record" — both state that the user's own file is never touched. In-row progress text is fed by the transfer callbacks. Sheets: `HatDetailSheet` (every field + locations, flagging `Missing`/`Unverified` paths and warning when a record carries a plaintext key), `HatExportSheet` (JSON with an opt-in "include the decryption key" toggle that warns what sharing it means), `HatImportSheet` (paste or open a file, single object or array, preview before importing). `Hat` gained `Identifiable` for SwiftUI. **Shipped invisible, then fixed:** the pane was unreachable on first run — `HomeView`'s sidebar listed its cases in two *hardcoded arrays*, so a new enum case compiled cleanly, satisfied the exhaustive detail switch, and simply never appeared. `WalletPane`'s own doc comment claimed the sidebar and the detail switch "can never drift apart", which was false. The sidebar now derives from `allCases` grouped by a new `WalletPane.Group`, so adding a case is the only edit a new pane needs and forgetting the detail arm stays a compile error. **Lesson for the phase log:** "it compiles" was not verification of a navigation change — nothing about a missing array entry is a type error. The check that would have caught it costs nothing: compile `WalletPane.swift` with a five-line driver and print what the sidebar will render. **That driver is now `tools/sidebar-check/run.sh`** — it takes a second, needs no app build, and exits non-zero on an unreachable pane; run it after any change that adds or regroups a pane.

> **▶ Phase 8.4.5 (2026-08-13).** `DiskService` + `HatSyncService` — the `DataSyncManager` port, where 8.4.1–8.4.4 combine. **`DiskItem`** (accepts `id` or the index's `did`), **`DiskService`**: `put` / `carve` / `get` (params `{id}`) / `check` (single + ≤200-id batches, matching the Java chunking), riding the streaming `callUploadingFile` / `callDownloadingToFile` added in 8.4.1 — `FapiCalling` grew those two as requirements with defaults that throw, so JSON-only stubs keep compiling but can't silently pretend a transfer happened. **`HatSyncService.upload`** is the two-HAT flow: fresh 32 B symkey per upload → `FileCipher` to a temp file → the cipher file's own DID → `kCipher` = symkey sealed to the owner's pubkey (`AsyOneWayCipher`) → `disk.put`/`disk.carve` → cipher HAT (`id`=cipher DID, `rawDid`, `kCipher`, `locas=[(sid)…]`) → `cipherIds` link on the raw HAT. `uploadRaw` stores plaintext for world-readable content-addressed docs (no cipher HAT, no key). `shareableHat(from:)` builds the IM message body — raw HAT + plaintext `key` + the cipher's DISK locations — and deliberately does **not** store it, since the local copy has no business carrying a plaintext key. **`download`** tries the three sources in Android's order: direct locations (unencrypted), then per cipher id the **plain-key path** (works with no cipher HAT and none of the sender's keys — the IM recipient's path, so it goes first), then the **kCipher path** (unseal with our privkey). **Nothing from DISK is trusted**: the cipher file is hashed against the DID it was requested under *before* a decrypt is spent on it, and the plaintext is hashed against the raw DID before it is kept; any failure deletes the output. Every failed attempt appends a reason and the accumulated diagnostics travel in the thrown error — a transfer that quietly finds nothing is otherwise undiagnosable. Wired as `ActiveSession.disk` / `.hatSync`, with a new `Preferences.preferredDiskServiceSid` so uploads are tagged `(sid)…` (survives the server changing address) rather than `fudp://host:port`. 18 tests against `FakeDiskServer`, an in-process content-addressed DISK: round trips through both key paths, a cross-identity IM hand-off (sender uploads, recipient with different keys downloads from the message HAT alone), plus the misbehaving-server cases that prove the verification is load-bearing — corrupted bytes rejected, and a *substituted but internally valid* cipher file (a real file, encrypted correctly, just not the one asked for) caught by the plaintext DID check.

> **▶ Phase 8.4.4 (2026-08-13).** `FileVault` — the reference-not-copy file layer, where the 8.4 decision is actually enforced. `registerFile(at:)` hashes the file (streaming `Hash.doubleSha256(fileAt:)`), stores a `Hat` whose only location is `local://<original path>`, and records a ``HatLocal`` stamp (size + mtime); **nothing is copied**. Registering content that is already known adds the second path as another location instead of duplicating the HAT — identical bytes are one DID. `resolve(hatId:)` is the guard that buys back what copying was providing: it stats each `local://` path, trusts an unchanged stamp (so the common read costs one `stat` and no hashing), re-hashes when the stamp is missing or stale, and then either re-stamps (touched but unchanged), prunes (moved/deleted), or **detaches** (edited in place) — returning `.available` / `.unavailable` / `.modified(url:newDid:)`, the last so the UI can offer "register as a new version". Candidates include the app copy at `data/<did>` even when unlisted (Android's fallback after a download). **A `local://` path that arrived inside someone else's HAT can never serve unrelated bytes**: with no stamp of ours it is always re-hashed, and a mismatch prunes it — writing that test caught a real design bug, since the first cut reported `.modified` for it, which would have invited "save as new version" for a file we never owned; `.modified` is now only ever reported for a path this vault had stamped. `materialize(hatId:)` copies into app storage (idempotent, survives losing the original), `removeLocalData` drops local bytes but keeps the record, and `delete` removes app-managed copies **only** — deletion is decided by whether the path is inside `dataDirectory`, not by the sidecar's flag, so a mislabelled record still can't delete a user's file. `ActiveSession.dataDirectory` sits beside the per-main `store.sqlite`, so file bytes inherit the same per-identity isolation the database has. 19 tests, nearly all of them the failure modes copying used to prevent.

> **▶ Phase 8.4.3 (2026-08-13).** `Hat` + `HatsStore` — the local HAT database (Android's `HatManager`, a `LocalEntityManager`: no chain sync, no FEIP). **`Hat`** mirrors `data/fcData/Hat.java` field for field, with three details that look like typos and are not: **`Leaked` is capitalized** (Gson serializes Java field names verbatim), **field order is Hat's own fields → `objName` (FcObject) → `id` (FcEntity)** (Gson emits the declaring class before its superclasses), and **two encoders differing only in escaping** — `toJson()` calls `disableHtmlEscaping()` while `toBytes()`, whose output `checkIdWithCreate()` hashes into the DID, uses a bare `new Gson()` that escapes `< > & = '` as `\uXXXX`. > **▶ Phase 8.4.2 (2026-08-13).** `FileCipher` — the FAPI DISK cipher-file format, byte-identical to FC-AJDK. **Format** (verified by running the real `Encryptor.encryptFileBySymkey`, not inferred): UTF-8 JSON header `{"type":"Symkey","alg":"AesGcm256@No1_NrC7","iv":"<24 hex>"}` (Gson field order = `CryptoDataStr` declaration order, nulls omitted, 76 B) immediately followed by AES-256-GCM `ciphertext ‖ 16 B tag` — **one GCM pass over the whole file**, 12 B iv, 128-bit tag. # FreerForMac — Migration Plan

A fresh-start Swift/SwiftUI rewrite of the Android Freer cryptographic wallet + IM/mail suite. Target is a clean, idiomatic macOS-native app — not a line-by-line port.

## Decisions locked (2026-04-24)

| # | Decision |
|---|---|
| 1 | **Transport:** FUDP + FAPI only. **APIP is retired** and will not be ported. |
| 2 | **Blockchain parity target:** `freecashj`, which is a fork of bitcoinj (BitcoinCash branch, ~2019-11-15). Tx/Script serialization must be byte-identical to that fork. |
| 3 | **KDF:** Argon2id, `iterations = 3`, `memory = 65536 KiB (64 MiB)`, `parallelism = 1`, `derivedKeyLen = 32`. |
| 4 | **Mnemonic dropped.** No BIP39 on Mac (or Android going forward). Passphrase → Argon2id → 32-byte private key. |
| 5 | **Target:** macOS 14 Sonoma (`@Observable`, Swift 5.9+). |
| 6 | **Bundle ID:** `fc.freer.mac`. |
| 7 | **Signing:** Developer ID available; sign + notarize for distribution. |
| 8 | **Scope:** full feature parity with Android (wallet, keys, secret, multisig, tx, tools, qr, contact, im, mail). |
| 9 | **Phase ordering:** wallet first, IM second. |
| 10 | Android bugs are tracked in `<android-repo>/docs/android-issues-to-fix.md`; append as we find more. |

## Design principles

- **SwiftUI-first**, AppKit only for windowing/menus SwiftUI cannot express cleanly.
- **Swift Concurrency** (`async`/`await`, actors). No callbacks or `DispatchQueue.main.async` scattered in view models.
- **`@Observable` MVVM.** No app-wide singletons. The Android "Manager" pattern becomes per-identity scoped dependency containers, passed explicitly.
- **Per-identity isolation at the type level.** An `Identity` value owns its own storage handle, FUDP session, and services — the compiler prevents mixing identities' data.
- **`Codable` everywhere.** One JSON path. No Gson/Jackson dualism.
- **Zeroize secrets.** Passwords live in `Data` (or `UnsafeMutableBufferPointer<UInt8>`) and are explicitly zeroed after use. Never `String`.
- **No premature abstraction.** One concrete implementation per service until a second call site appears.

|---|---|---|

**Design notes:**
- Per-identity isolation enforced at the type level: every domain service takes an `Identity` and pulls its `EncryptedKVStore` from there. No global "current identity" singleton.
- Use cases = `async` functions returning typed results (`throws` rather than `Result<T,E>` — Swift's typed-throws still requires opt-in and Result fights `try`).
- Each store namespaces its keys (`settings:*`, `keys:*`, `contacts:*`) inside the shared per-identity `EncryptedKVStore` — one DB per identity, not one per concern.

**Cache architecture (Three Patterns).** FCH's `lastHeight` is on every chain entity — every cache becomes incremental.

| Pattern | Shape | Sync | Used for |
|---|---|---|---|
| **A** | Watermark-synced collection by `lastHeight` | Bootstrap once, then `lastHeight > localMax − 30` (reorg window) | `CashesStore` (the wallet's spendable cash set) |
| **B** | Cipher-always-stored + plaintext decryption overlay | Cipher rows persist; plaintext lives only in memory under the symkey | Reserved for future per-main encrypted artifacts |
| **C** | Cursor-paginated stream blob | Append on next-cursor, replace on filter change | `RecentActivityStore` (Transactions pane, key per-kind: all / incomes / expenses) |

**Wire / consensus gotchas worth not relearning:**
- **P2PKH spends require BCH-Schnorr.** ECDSA-DER is rejected by mainnet with the misleading error `Signature cannot be 65 bytes in CHECKMULTISIG`.
- **FCDSL `query` vs `filter`.** Both are separate fields on the POJO. `base.search` consumes `query` via `queryExecutor.executeQuery`; `base.cashValid` mode-1 reaches for `filter`. Mixing them up causes silent timeouts.
- **FUDP STREAM frames must be reassembled.** Responses ≥ ~1 KB span multiple STREAM frames sharing a `streamId`, with `offset` and `fin` only on the last. Decoding each as a complete AppMessage corrupts the receiver's state and breaks every call after the big one.
- **Bootstrap fallback:** `base.cashValid` mode-2 (`params: {fid}`) is the known-working bootstrap. Incremental `base.search` is fail-soft — on any error it falls back to mode-2.

**UX rules locked in (saved as feedback memory):**
- Every FID and every toast/error is click-to-copy with a green-checkmark flash (`CopyableText` in FCUI).
- Every truncated ID renders middle-elided: `head + "…" + tail`, never `prefix(N)`. Use `String.elidingMiddle` or `CopyableText.elidingMiddle`.

### Phase 8.4 — HAT + file management · ~5d · **Phase 9 prerequisite**

Port of Android's `HatManager` + `DataSyncManager` + `DataActivity`/`HatFileOpener`. A `Hat` is a **local-only** (no blockchain sync, no FEIP) file-metadata record: `id` = DID = hex `sha256x2(content)`, `locas` = list of locations (`local://<path>`, `fudp://host:port`, `(sid)<serviceId>`), plus the two-HAT cipher fields. IM file messages (Android `FileShareHelper`) serialize the **raw HAT JSON as the message content** with the plaintext `key` and DISK locas copied in — the receiver adds that HAT to its own store and downloads via the plain-key path. So this layer, wire-compatible with Android's `Hat.toJson()`, must exist before Phase 9.

**Two-HAT cipher model (`DataSyncManager` parity).** Upload: random 32 B symkey → encrypt file → cipher DID = sha256x2(cipher file) → `kCipher` = AsyOneWay-encrypt the symkey to the owner's own pubkey (same envelope as 7.6.3's `AsyOneWayCipher`) → `disk.put` (temp, `dataLifeDays`) or `disk.carve` (permanent) → create cipher HAT (`id=cipherDid, rawDid=rawHat.id, kCipher, size, locas=[(sid)… preferred, fudp://… fallback]`) → append cipherDid to raw HAT's `cipherIds`. Download: (1) raw HAT's remote locas direct — **hash-verify against the DID, servers are untrusted**; (2) per cipherId: plain-key path first (`rawHat.key`, works without the cipher HAT in the local DB — the IM receive path), then kCipher path (decrypt with live privkey); stream-decrypt; plaintext must hash back to the raw DID; write into the app data dir and add a `local://` loca. Accumulate per-attempt failure diagnostics into the surfaced error (Android's `diag` string — keep it, it's what makes DISK failures debuggable).

**The Mac difference — reference, don't copy (decision 2026-08-13).** Android copies every imported file into `filesDir/data/<did>` because SAF content URIs aren't stable. On macOS (unsandboxed SwiftPM build) we register the **original file's path** as the `local://` loca — no copy, no doubled disk usage, instant import even for GB files. Reference-mode guard: a `HatLocal` sidecar (persisted next to the wire `Hat` in the store row, **never** serialized into IM/export JSON) records size+mtime per referenced path at registration; every access `stat`s the file — missing → drop the loca (self-heal); size/mtime changed → re-hash; hash ≠ DID (edited in place) → detach the loca and offer re-register-as-new-version (`preDid`/`srcDid` links). Cost: one `stat` per access; re-hash only on actual change. Downloads and explicit "materialize a copy" land in `Application Support/FreerForMac/<mainFid>/data/<did>` (checked as an implicit loca, like Android's `filesDir/data/<did>` fallback). A received HAT's foreign `local://` paths simply fail the `stat` and are ignored. If the app is ever sandboxed for distribution, `HatLocal` grows security-scoped bookmark data — field reserved now.

### Phase 9 — Mail + IM · 10d · **largest feature chunk**

**Ordering: Mail first (9.1), IM second (9.2)** — reversed from the original outline on 2026-08-14. Mail is a *carve-and-sync* feature with exactly the shape we have now shipped twice: an on-chain FEIP entity whose payload is an encrypted `CryptoDataStr` envelope, paged out of `base.search`, decrypted locally, merged into a per-main store — Contacts (7.6.2b/7.6.3) and Secrets (8.2) are the same program. IM is a *live-session* feature: rooms/squares/teams, an inbound FUDP push path, per-session key agreement, message adapters. Android's `mail/` is 4.7 k lines against `im/`'s 26 k. Doing Mail first reuses machinery that is already load-bearing, keeps the phase's first deliverable close, and — the real reason — the two prerequisites Mail forces out (AsyTwoWay envelopes, carve-with-a-recipient-output) are both things IM needs anyway.

#### Phase 9.1 — Mail · ~4d · ✅ complete (2026-08-14), pending the live acceptance run

Port of Android's `mail/` (`MailActivity` / `CreateMailActivity` / `ReadMailActivity` / `DeleteMailActivity` / `MailDeletedActivity` / `SetNoticeFeeActivity`) + `manager/MailManager`. FEIP protocol **`Mail` sn 7 ver 4**, ops `send` / `delete` / `recover`; the notice fee is its own protocol, **`NoticeFee` sn 10 ver 1**.

A mail is one OP_RETURN carve: `{"type":"FEIP","sn":"7","ver":"4","name":"Mail","data":{"op":"send","cipher":"<CryptoDataStr JSON>"}}`, in a tx that **also pays the recipient** — that output is what makes `to` an indexable field and what delivers the notice fee. So unlike a contact or secret carve, the sender's FID and the recipient's FID are public; only the body is sealed.

#### Phase 9.2 — IM · ~6d · in progress

Port of Android's `im/` (26 k lines against Mail's 4.7 k) + `FC-AJDK`'s `data/fcData` IM entities. Unlike Mail, **almost none of this is on-chain**: an IM message is a live FUDP payload with a local encrypted copy, so the parity surface is a *binary wire format* and a *handler protocol* rather than a FEIP carve. Squares and Teams are the exceptions — their membership is a FEIP entity — and they arrive late, after the delivery path they ride on works.

The sub-phase order below is bottom-up on purpose: the message, then where it is kept, then the key that seals it, then the path it travels, then the three group flavours, then the pane. Each layer is testable without the one above it.

## Key risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | **FUDP parity.** Custom protocol; any byte-level drift breaks interop with existing servers. | Interop harness against a live Android-spun server as early acceptance test (end of Phase 4). |
| R2 | **Tx serialization parity** with freecashj (BCH 2019-11-15 fork). Sighash quirks, BIP143-style preimage details. | Parity harness with captured tx hex fixtures (end of Phase 2). Do not advance to Phase 3 until it is green. |
| R3 | **Schnorr compatibility.** freecashj's Schnorr may predate BIP340 finalization and use non-standard R/tags. | Inspect freecashj source, mirror exactly. Add vectors from a freecashj-signed fixture set. |
| R4 | **macOS sandbox entitlements** — Keychain, camera (QR), microphone (voice msg), network-client, file-access for downloads. | List entitlements up front in Phase 0; add `.entitlements` file; test each in its feature's phase. |
| R5 | **Argon2 Swift library maturity.** Pure-Swift Argon2 implementations are rare. | Use `CatCrypto` (wraps reference C impl) or bundle `argon2` as a SwiftPM system target. Bench on target hardware. |
| R6 | **Single-engineer scope.** ~44 days is long; priorities may shift mid-flight. | Each phase produces a runnable artifact; pause-points are natural if scope trimming is needed. |
